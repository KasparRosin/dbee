# Decisions

> **Last reviewed:** 2026-11-23 · **Last updated:** 2026-11-26 · **Change:** minor (a page opens through the desktop's opener, not a library; a query result sorts in memory, among the rows held)

Significant decisions, newest last. Add an entry for every significant dependency, platform or process choice.

## 2026-10-15: Name `dbee`, app ID `dev.rosin.dbee`, homepage `https://dbee.rosin.dev`

- **Decision:** The product is `dbee` (lowercase everywhere), with app ID `dev.rosin.dbee` and homepage `https://dbee.rosin.dev`.
- **Why:** One stable lowercase name keeps binaries, package ids and the website consistent.

## 2026-10-15: Desktop only, no browser build

- **Decision:** dbee ships as a native desktop app. There is no web build and no wasm target.
- **Why:** Browsers cannot open database connections (raw TCP to PostgreSQL, MySQL or SQL Server).

## 2026-10-15: Full platform matrix

- **Decision:** Linux x86_64, aarch64 and riscv64; macOS universal; Windows x64, x86 and arm64; FreeBSD.
- **Why:** A database client is used on whatever machine the developer has, and a pure-Rust stack makes the wide matrix cheap.

## 2026-10-15: Signing is optional

- **Decision:** Builds ship unsigned until signing secrets exist; the workflows warn instead of failing.
- **Why:** Certificates cost money and need the owner's accounts; the pipeline must work before they exist.

## 2026-10-15: Self-contained workflows

- **Decision:** The workflows use no shared tooling from outside this repository; third-party actions are pinned to commit SHAs.
- **Why:** The repository must build and release on its own, and it should be easy to audit.

## 2026-10-15: Rust 1.99 minimum

- **Decision:** `rust-version = "1.99"` in `[workspace.package]`, edition 2024.
- **Why:** A single recent toolchain keeps the code modern and the support matrix small.

## 2026-10-15: Licence MIT OR Apache-2.0

- **Decision:** dbee is dual-licensed `MIT OR Apache-2.0`.
- **Why:** The common permissive pair for Rust projects; contributors and users may pick either.

## 2026-10-15: Owner Kaspar Rosin, an independent project

- **Decision:** The owner and publisher is Kaspar Rosin. dbee is an independent project and not part of any app family.
- **Why:** One accountable owner for releases, signing and the licence line.

## 2026-10-15: Target app Beekeeper Studio 5.5.7, observed black-box only

- **Decision:** The parity target is Beekeeper Studio 5.5.7. It is only observed from outside, as a user would (clean room): its source, bundle, settings and traffic are never read.
- **Why:** dbee must be original work, and a black-box target keeps the licence of dbee clean.

## 2026-10-19: Docker test servers, Postgres 14 + newest

- **Decision:** Driver and SSH tests run against local Docker containers that `cargo xtask testdb up` starts (compose project `dbee-testdb`): Postgres 14, the oldest supported major, and the newest released major (the `pgnew` row of `SERVICES` in `xtask/src/testdb.rs`, 18 on 2026-10-19 because `postgres:19-alpine` was not yet published), both with TLS and the same synthetic seed, plus an SSH server for tunnels. Ports are random on `127.0.0.1`, the password and key passphrase are generated, and `target/testdb/env.json` tells the tests where everything is. Without Docker the tests print `SKIPPED`; `DBEE_REQUIRE_ORACLES=1` makes that a failure.
- **Why:** Testing the oldest and newest majors catches catalog and type differences across the supported range, and a fixed seed gives every test the same odd identifiers, exotic types, a million rows and a 20 MB cell. Containers keep tests away from real servers, `~/.ssh` and the SSH agent, and one compose project is easy to start, inspect and remove.

## 2026-10-19: Secrets in the OS keyring via keyring-core, pure-Rust Secret Service

- **Decision:** Passwords and key passphrases are stored through `keyring-core` 1 with one store per platform: `zbus-secret-service-keyring-store` (feature `crypto-rust`) on Linux and FreeBSD, `apple-native-keyring-store` (`keychain`) on macOS, `windows-native-keyring-store` on Windows. The connections file never holds a password. Tests and agent runs use an in-memory store.
- **Why:** The zbus store with pure-Rust crypto needs neither `libdbus-sys` nor OpenSSL, which the licence and build rules forbid. Without a Secret Service the store reports an error and the UI offers to continue without saving.

## 2026-10-19: russh with ring for SSH tunnels

- **Decision:** SSH tunnels use `russh` 0.64 in-process, with default features off and `ring`, `rsa` and `flate2` on, over `tokio`. Host keys are checked against `~/.ssh/known_hosts` by dbee's own reader (`crates/ssh/src/known_hosts.rs`: tabs, `@revoked`, `@cert-authority`, wildcards, hashed names and case, as OpenSSH reads it): an unknown host is refused with its SHA256 fingerprint until the user accepts it, and is then learned; a changed key, a key of another type than the recorded one (what an interception looks like) and a revoked key are refused and cannot be overridden. Logins use the agent, a key file (with its passphrase) or a password. The `rsa` crate carries advisory RUSTSEC-2023-0071 (the Marvin timing side channel); it matters little for a client that signs with its own key locally, and nothing else in dbee uses RSA decryption.
- **Why:** A library tunnel needs no `ssh` binary on the machine, works the same on every platform (including the Windows agent pipe), and reports each failure as a typed error the UI can turn into a prompt (host key, passphrase, password). `ring` keeps `aws-lc-sys` and `aws-lc-rs`, which the build rules forbid, out of the tree.

## 2026-10-19: tokio-postgres over the simple-query text protocol (values exactly as printed, no prepared statements for data)

- **Decision:** `dbee-pg` talks to Postgres with `tokio-postgres` 0.7 on the shared `tokio` runtime. Data travels only over the simple-query protocol, so every value arrives as the text Postgres prints for it (`1.50`, `2024-01-02 03:04:05`, `{"a": 2, "b": 1}`), and dbee shows that text unchanged. No prepared statement carries data: values dbee writes or filters on go into the SQL text as quoted literals with an explicit cast, which is safe because every session runs `SET standard_conforming_strings = on` and tokio-postgres always starts with `client_encoding=UTF8`. Connections through an SSH tunnel use `Config::connect_raw` on a tunnel channel; cancel requests go the same way. Server notices are not logged, since they can quote data.
- **Why:** The binary protocol would need a decoder per type and would still re-format values (numeric scale, time zones, intervals, exotic and user-defined types); the text protocol is exact for every type, including ones dbee does not know. tokio-postgres is pure Rust, MIT/Apache, maintained, and lets the caller supply the stream and the TLS layer.

## 2026-10-19: rustls with ring and the OS certificate verifier

- **Decision:** TLS uses `rustls` 0.23 (default features off; `ring`, `std`, `tls12`) through `tokio-postgres-rustls` 0.14 (`ring`). The modes follow libpq: `disable`; `prefer` and `require` without verification (`prefer` falls back to plain when the server has no TLS or the handshake fails; `require` checks the chain when a CA file is set); `verify-ca` checks the chain against the CA file only, and is refused without a CA file; `verify-full` checks the chain and the configured host name, also through a tunnel. The roots are the CA file's certificates when one is set, otherwise (`verify-full` only) the operating system's through `rustls-platform-verifier` 0.7. `verify-ca` against the system roots is refused on every platform, as libpq refuses it: a chain check alone would accept any publicly trusted certificate for any host. `tokio-postgres` is pinned exactly (`=0.7.18`) because dbee-pg classifies its errors by their texts.
- **Why:** `ring` keeps `aws-lc-sys` and `aws-lc-rs` out of the build (the build rules forbid them), and the platform verifier uses the trust store and policies the user already manages instead of a bundled root list (`webpki-roots` is forbidden too).

## 2026-10-20: egui_extras for the grid, egui_kittest for UI tests

- **Decision:** `crates/ui-egui` takes `egui_extras` 0.36 (default features off: no image loaders, no syntax highlighting) for its table layout, and `egui_kittest` 0.36 as a dev-dependency, which runs `DbeeApp::ui` frame by frame without a window. Both are from the egui project, versioned with egui, MIT OR Apache-2.0.
- **Why:** The result grid needs virtual scrolling over thousands of rows with resizable columns, which `egui_extras`' table gives; writing our own would be a second grid to maintain. kittest drives the real UI code in tests (frames, input, accessibility queries) with no display, so the UI tasks get tests that run in `cargo xtask ci`.

## 2026-10-23: rfd file pickers through the XDG desktop portal, no GTK

- **Decision:** `crates/ui-egui` opens file pickers (the SSH key's "Change…", the CA file's "Choose…") with `rfd` 0.17, default features off and `xdg-portal` and `wayland` on (MIT). On Linux and the BSDs that asks the XDG desktop portal over D-Bus, through the system's `libdbus-1` loaded at run time (no `libdbus-sys` crate), and falls back to `zenity` when there is no portal; macOS and Windows use their native pickers. The picker runs on a thread of its own and sends the chosen path back to the UI thread, so the window keeps drawing while it is open on Linux, the BSDs and Windows; on macOS rfd shows the panel modally on the main thread, so the window waits while it is open, as it does for any macOS open panel. When no picker can open, the form says so under its buttons instead of waiting. Tests and agents never open it: they set a key path by saving a connection.
- **Why:** rfd's `gtk3` backend would bring GTK, which the build rules forbid, and a picker written for egui would be a second file browser to maintain. The portal gives the desktop's own picker, also inside sandboxes such as Flatpak.

## 2026-10-26: The toolchain is pinned in `rust-toolchain.toml`

- **Decision:** `rust-toolchain.toml` names an exact release (`1.99.1`, the minimal profile with clippy and rustfmt), and it is bumped by hand. `rust-version = "1.99"` stays the minimum.
- **Why:** A new compiler invalidates every cached build. With `stable`, an update of the machine's toolchain rebuilt the whole dependency tree in the middle of the work; a pinned release changes only when the repo says so, in a commit of its own.

## 2026-10-28: M2 is three databases, before import and export

- **Decision:** M2 is "Three databases": a driver interface, then MySQL/MariaDB and SQLite with the full M1 workflow. Import and export move to M3 (M4 since 2026-11-08).
- **Why:** The engine still names Postgres types, and export and import should be written once against the interface, not once per engine. Two more databases also widen who can use dbee daily.

## 2026-10-28: SQLite's public-domain code is allowed

- **Decision:** The licence allowlist gains SQLite's public-domain dedication, for the SQLite library compiled in by `libsqlite3-sys` (through `rusqlite` with `bundled`). The crates themselves are MIT.
- **Why:** SQLite is public domain and has no licence text to put on the list. Linking it in keeps dbee one binary with no system library to find.

## 2026-10-30: A driver interface: traits in dbee-driver, drivers at L4, the engine names none

- **Decision:** `dbee-driver` (L3) holds the interface every database driver implements: the `Driver`, `Connection` and `Cancel` traits, one error type (`DbError`), `ServerInfo`, `Target`, the caps, the apply gate, the shared TLS setup and the `CatalogBuilder`. The drivers (`dbee-pg` now; MySQL/MariaDB and SQLite next) sit at L4, and `dbee-drivers` (L4) is their one list, which only the apps and test code use. `cargo xtask layers` keeps the engine and the UIs from taking a driver crate except as a dev-dependency.
- **Families:** A driver serves a family of database types: the MySQL driver serves MySQL and MariaDB, and the Postgres driver can later serve Postgres-like servers. It names the types it opens, and each connection says which SQL dialect its server speaks.
- **Why:** Each engine plugs in the same way, and shared logic (TLS, the apply gate, catalog building) exists once. Adding an engine is one driver crate, one dialect file and one registry line. More exactly, as "Adding an engine" in `architecture.md` lists it: one driver crate, one dialect file, one kind file, one registry line, the enum variants and the layers line.

## 2026-10-30: dbee's own MySQL client on mysql_common

- **Decision:** `dbee-mysql` speaks MySQL's client/server protocol itself. `mysql_common` 0.38 (MIT OR Apache-2.0, default features off: no zlib, no derive macros) gives the packet structs, the login scrambles and RSA; the I/O is dbee's own: TCP or a channel through the SSH tunnel, upgraded to TLS by `tokio-rustls` 0.26 (default features off; `ring`, `tls12` and `logging`; already in the tree through `tokio-postgres-rustls`) with the same rustls verifier as Postgres. Values travel over the text protocol (`COM_QUERY`), as the server prints them. MariaDB is a flavor of the same driver, told by `@@version`, not by the connection's type.
- **Logins:** `mysql_native_password`, `caching_sha2_password` (the fast path; the full path over TLS, or with the password encrypted with the server's RSA key) and `sha256_password` (the same rule). The password is never sent in clear without TLS; any other method (`mysql_clear_password` among them) ends the login before the password is used. Without TLS the RSA exchange keeps the password from a listener, not from a man in the middle, who can hand over a key of their own; TLS or the SSH tunnel protect against that.
- **Hostile servers:** every length, count and offset a server sends is checked, and every `mysql_common` parser dbee feeds server bytes to is fuzzed. Two of them panic on hostile input (the greeting parser on a challenge length of 128 to 135, the RSA key's DER parser on a length past its data), so dbee checks those bytes against the documented layouts before handing them over.
- **Why (checked 2026-10-28):** `mysql_async` 0.37's TLS needs `webpki-roots` (`rustls-tls`) or OpenSSL (`native-tls-tls`), both forbidden, and takes no stream of dbee's, so no tunnel channel; `sqlx` opens its own socket (a loopback forward) and checks certificates against the OS's roots, not through the OS verifier. `mysql_common` has no networking of its own.

## 2026-10-30: MySQL 5.7's TLS is out of rustls's reach; plain direct and SSH work

- **Decision:** The official `mysql:5.7` image offers TLS only with DHE-RSA ciphers on TLS 1.2, which rustls never speaks. dbee tells this from the TLS failure itself (the server's handshake alert), not from the version: `require`, `verify-ca` and `verify-full` fail with a TLS error that says the server offers only ciphers dbee does not support and points to an SSH tunnel, and `prefer` connects without TLS, as libpq's `prefer` does after a failed handshake. Plain direct connections and connections through the SSH tunnel work.
- **Why:** No new TLS stack (OpenSSL and aws-lc stay out) and no 5.7-only code path. The tunnel encrypts the link instead.

## 2026-10-31: MySQL's server key only without encryption or when allowed; per-type connection options

- **Decision:** On a link without TLS, `caching_sha2_password` and `sha256_password` protect the password with an RSA key the server sends, which dbee cannot check. dbee fetches that key when the user chose no encryption (`disable`) or the SSH tunnel encrypts the link, with no warning. When the user wanted encryption and the link ended up plain on a direct connection (`prefer`, with TLS failed or not offered, which an attacker on the link can force), the login is refused before the password is used, unless the connection's `allowPublicKey` option is on; then it goes ahead with a warning on the connection. `require` and the `verify-*` modes always have TLS. dbee follows MySQL's own clients in refusing the key on a link the user wanted encrypted, but allows it when the user chose no encryption.
- **Options:** A database type's own settings are on/off options: `ConnectionConfig.options` (by id, left out of the file when empty, keys a build does not know kept) and `KindInfo.options` (id and label). MySQL lists `allowPublicKey`, and MariaDB inherits it through its row; Postgres and SQLite list none. The connection form shows them from M2.15.
- **Why:** Whoever sits on a plain link can hand dbee a key of their own and read the password. Where the user asked for no encryption, or the tunnel gives it, there is nothing to protect against; where the user wanted encryption, that choice must not be undone silently. One options map keeps engine-only settings off the shared struct.

## 2026-11-01: dbee reads MySQL's column definitions itself; MariaDB's JSON from its extended metadata

- **Decision:** `dbee-mysql` parses every column definition itself, from MySQL's and MariaDB's documented layout, on both flavors, instead of with `mysql_common`'s `Column`: one code path, every length checked against the packet, fuzzed, and held to `mysql_common`'s reading of the same definitions on every test server. From a MariaDB server that offers it, dbee asks for `MARIADB_CLIENT_EXTENDED_METADATA` and reads the extra field only when it was agreed; its format `json` makes a column JSON, and its other keys are skipped.
- **Classes:** A column's class comes from its type, flags, character set and length: `TINYINT(1)` is true/false (every server sends the declared width), strings and blobs in the `binary` character set hold bytes, and so do `BIT`, geometries and vectors, whose values are shown as `0x` and hex rather than as text they would not survive. A type dbee does not know (one a newer server adds) is shown as text, and the queries that touch it go on working.
- **Why:** MariaDB has no JSON type: without the extended metadata a JSON column looks exactly like a `LONGTEXT` with a binary collation, and `mysql_common`'s parser cannot read the definitions once the metadata is on.

## 2026-11-03: rusqlite with the bundled SQLite

- **Decision:** `dbee-sqlite` is built on `rusqlite` 0.40 (MIT) with `bundled`, which compiles SQLite (public domain) into dbee through `libsqlite3-sys` (MIT), and with `column_decltype`, which gives a result column's declared type. Every SQLite call runs on a blocking thread, one operation at a time on each connection; an apply runs one blocking call per statement, so its gate is read between them.
- **Facts measured (SQLite 3.53.2), which the driver follows:**
  - SQLite ends a statement at a NUL outside a string literal and runs the part before it (`DELETE FROM t<NUL> WHERE id = 1` deleted every row); one inside a literal is an error. The driver refuses statement text holding a NUL before SQLite sees it, and the dialect's rule stays that statements cannot hold one.
  - `sqlite3_interrupt` sent while no statement runs has no effect on the next one. dbee sends it only while a call of its own runs, so a cancel never reaches a later call.
  - `CAST(x AS TEXT)` of a real is SQLite's own form, neither the shortest nor a fixed number of digits (`5e-324` prints `4.9406564584124654e-324`), so reals become text through SQLite itself.
  - rusqlite panics on a result column name or declared type that is not UTF-8, which a crafted file's schema can hold. Before it reads them, the driver checks the schemas' names and types and refuses such a result.
  - The bundled build reads `file:` names as URIs even without the URI flag, so the driver opens a file by its absolute path.
  - `PRAGMA quick_check(1)` reads the whole file (about 150 ms for 65 MB). Opening reads `sqlite_schema` instead, which still refuses a file that is not a database or whose schema is damaged; damage elsewhere shows when it is read. A path that is no regular file is refused before it is opened (a FIFO would wait for a writer), the open is bounded by the 15 s connect timeout, and the file is closed on a blocking thread, since closing can write (a WAL checkpoint, a rollback).
  - SQLite ends a transaction itself when an interrupt stops a write in it, and may when a write fails with `SQLITE_FULL`, `IOERR`, `BUSY` or `NOMEM`; a `BEGIN IMMEDIATE` that fails (a locked or a read-only file) starts none. The apply session therefore has its own rollback step (by default it sends `ROLLBACK`): SQLite's reads in the same call whether a transaction is open, and when none is, there is nothing to undo, as on the other engines, and no lost connection.
- **Why:** SQLite in the binary means no system library to find, and the same SQLite on every platform. rusqlite is the established binding; dbee uses it as a library.

## 2026-11-03: SQLite tables without a key are edited by their rowid; isolated runs keep SQLite to their own folders

- **Decision:** An ordinary SQLite table (not a view, a virtual table or a `WITHOUT ROWID` table, which always has a primary key) with no primary key and no NOT NULL unique key is keyed by its rowid. The catalog lists the rowid as a hidden leading column, named by the first of `rowid`, `_rowid_` and `oid` that no column takes (ignoring ASCII case, as SQLite does), and the page reads it beside the visible columns; the grid, sort, filters, copies and the value view never show it, and an insert never writes it. A table whose columns take all three names, and a virtual table, take no edits and say why.
- **Known limit:** SQLite's `VACUUM` may change the rowids of a table without an `INTEGER PRIMARY KEY` (SQLite's documentation of `VACUUM` says so). An edit staged before another process vacuums the file could then find a different row; Apply's one-row rule only catches a row that is gone. Not handled.
- **Decision:** An isolated run (`cargo xtask run-isolated`) lists its folders in `DBEE_ALLOW_DIRS`: its throwaway home and `target/` (with `DBEE_ALLOW_TARGETS` set and `DBEE_ALLOW_DIRS` not, no folder). The folders go to the driver in `Target::allowed_dirs`. A file driver checks its file inside its bounded open, with `dbee_driver::allowed_file` (links followed, `..` gone; a file not there yet by its folder), and opens the path that check resolved, on both connections; a file outside is refused with the `config` code, and nothing is opened or made. The engine checks only what needs no filesystem read: a server's target, and the SSH server any config names; a database file takes no SSH tunnel at all. While folders are set, SQLite's driver installs an authorizer (the `hooks` feature of `rusqlite`) that refuses every `ATTACH`, and `PRAGMA temp_store_directory` and `data_store_directory` with a value (compared by name), with the hint "This isolated run lets SQL open no other file, so ATTACH and VACUUM are refused." Normal runs keep `ATTACH` and `VACUUM INTO`.
- **Facts measured (SQLite 3.53.2):**
  - `VACUUM INTO '<path>'` reaches the authorizer as an `ATTACH` of that path, and a plain `VACUUM` as an `ATTACH` of `''` (its temporary database). Refusing `ATTACH` refuses all three, whatever the name, a `file:` URI and `:memory:` included, with `SQLITE_AUTH` (23); no file is made. dbee's message adds a hint that the run lets SQL open no other file.
  - `SQLITE_LIMIT_ATTACHED` = 0 also refuses all three, as "too many attached databases - max 0"; the authorizer was chosen for its clear code and because it is SQLite's documented way to keep SQL from what it may not do.
  - `ATTACH` opens with the main file's flags, so on a file dbee opened without leave to make one it opens only a file that is there.
  - `load_extension()` is off: "not authorized". The modules compiled in are `dbstat`, `fts3`, `fts4`, `fts5` and `rtree`, which read only the databases on the connection.
  - `PRAGMA temp_store_directory` and `data_store_directory` move SQLite's own files to another folder, process-wide; the authorizer sees them as pragmas with their value.
- **Why:** `rowid` counts as a real key within an edit session. The isolation rule must hold on every path into a file, and parsing paths is where it would leak, so the driver refuses the statements, not paths.

## 2026-11-05: The connection screen picks the database type first

- **Decision:** A new connection starts with one card per database type (`DbKind::ALL`), then the form for the chosen type, with the type and Change engine on its title row. A type this build has no driver for shows "Upcoming" and cannot be chosen. The form's rows come from the type's settings and options in `KindInfo`, so the UI names no type. A URL's scheme picks the type. A connection opened from the saved list or Recent keeps its type, and its Fill from URL takes that type's URLs only; one saved during the edit, or a Duplicate, can still change type. A config holds only what its type's settings use. After New file…, every `connection.test` and `connection.open` sends `createFile: true` until a connect succeeds; the engine refuses it for a read-only connection.
- **Why:** The type decides which fields make sense, so it comes first; a connection opened from the list keeps its own, while one still being made can be corrected.

## 2026-11-06: MySQL values with a backslash or a NUL are written as hex

- **Decision:** A value dbee writes into MySQL or MariaDB SQL text (an edit, a filter, a key) that holds a `\` or a NUL is written `_utf8mb4 X'…'`, the uppercase hex of its UTF-8 bytes; every other value is `'…'` with `'` doubled.
- **Why:** whether `\` escapes depends on the session's `sql_mode` (`NO_BACKSLASH_ESCAPES`), so a quoted value with one would mean different text on different sessions. Hex reads the same in every mode, and the introducer keeps it a character string, so `LOWER`, `LIKE` and collations treat it as `'…'`.

## 2026-11-06: A NUL outside a string literal is refused on MySQL

- **Decision:** On MySQL and MariaDB a query tab's statement holding a NUL character outside a string literal is refused before it is sent; one inside a literal is sent (it is a character there).
- **Why:** measured on all five test servers, a NUL outside a literal is a syntax error when text follows it, but ends the statement there when only spaces follow, and is ignored inside a `/* */` comment. The server must run what the editor shows, so every such NUL is refused, as on SQLite, which cuts a statement at one (`DELETE FROM t<NUL> WHERE id = 1` deleted every row).

## 2026-11-06: The query connection's database comes from MySQL's session tracking

- **Decision:** The engine keeps the database the query connection is in: the settings' when it opens, each `USE` it sends, and where the server says each statement left it, from MySQL's session-state tracking (`SESSION_TRACK_SCHEMA` in its OK packets). dbee sends no statement of its own to ask. After a run whose text names `session_track` the driver trusts the reports no more on that connection, and the engine sends a tab's `USE` before every run.
- **Why:** the tab's database chip must say where a run goes. A `SELECT DATABASE()` after each run would clear the warnings a user reads next with `SHOW WARNINGS`; a statement that turns the tracking off would leave the reports silent, and a run in the wrong database is worse than a `USE` too many.

## 2026-11-06: Connections-file entries dbee cannot read are kept and written back

- **Decision:** The connections file's saved and recent entries are read one by one. An entry this build cannot read (a database type it does not know, say) is kept as it is and written back on every save, and a warning gives their count; a file that is not JSON at all is moved aside as `connections.json.bad`.
- **Why:** an older dbee must never delete the entries a newer one wrote.

## 2026-11-06: The MySQL browse connection runs in autocommit

- **Decision:** The browse connection's session setup also runs `SET SESSION autocommit = 1`; the query connection keeps the server's mode.
- **Why:** on a server whose default is autocommit off, page reads would share one long `REPEATABLE READ` snapshot (stale pages) and hold metadata locks that block other sessions' DDL.

## 2026-11-06: `LIKE` escapes with a backslash on every engine

- **Decision:** The filter bar's `like`, `not like`, `ilike` and `not ilike` take `\` as the escape on every engine, as Postgres's `LIKE` does by default: MySQL's and MariaDB's patterns end in `ESCAPE _utf8mb4 X'5C'`, SQLite's in `ESCAPE '\'`, Postgres's in nothing. Each is a field of the engine's dialect `Rules`.
- **Why:** measured on the seven test servers and SQLite, `50\%` found "50%" on Postgres, MySQL 5.7 and MariaDB, but nothing on MySQL 8.0 and later (no escape under `NO_BACKSLASH_ESCAPES`) and SQLite (no escape unless one is named). The hex form reads the same whether or not `NO_BACKSLASH_ESCAPES` is set, where `'\'` would not.

## 2026-11-06: Foreign keys are on for every SQLite connection

- **Decision:** dbee runs `PRAGMA foreign_keys = ON` when it opens a SQLite file, so `ON DELETE CASCADE` and the other foreign key actions run, and an edit that breaks a foreign key fails. The setting belongs to the connection, not to the file.
- **Why:** the schema's foreign keys mean what they say, and other database tools do the same. A program that keeps foreign keys off against the same file sees cascades it did not expect after dbee deletes a row.

## 2026-11-06: A cancel is sent again until the statement ends, and never reaches a later one

- **Decision:** the job that runs a statement sends the cancel itself, again after 1 s and then every 2 s while the statement has not ended, and waits for each request to arrive before it goes on. Each driver starts no statement while a request is on its way.
- **Why:** a cancel that reaches the server before the statement does is lost. A cancel that lands on the next statement would stop work the user did not stop.

## 2026-11-06: A file opens as it was saved

- **Decision:** a database file that a saved connection names (links followed, `.` and `..` gone) opens with that connection's name, colour and read-only setting, and a file dropped on the window while connected goes through the questions of closing the open connection.
- **Why:** opening a file that was saved as read-only must not make it writable.

## 2026-11-08: Each change to the connections file re-reads it under a lock

- **Decision:** A save, a delete, a duplicate and the recent list's touch at each open read `connections.json` again, apply only that change to what it holds, write it atomically (temp file, then rename) and keep the result as the session's copy, all under an advisory lock on `connections.json.lock` beside it (std's `File::lock`, no dependency), held for the read and the write only. A lock another dbee keeps for 5 s is an error the user sees, and nothing changes; so is a lock the file system refuses. A file over 4 MiB is not read: the store keeps its changes in memory, as for an unreadable file. The connection screen reads the file again after a disconnect.
- **Why:** one dbee per window (and the file manager starts one per file) each wrote its whole list from memory, so a second dbee's open wrote back an older list over the first one's save. The atomic write prevents a torn file, not a lost update.

## 2026-11-08: The connections file's version, and fields a build does not know

- **Decision:** The file says its `version` (1). Adding a field is free; renaming one, or changing what it means, moves `version` on; a build never writes a file whose version is newer than its own. The version is read before the rest, so a newer file is never moved aside as damaged, whatever its shape: the build reads what it can of it and keeps its changes in memory, with the warning "A newer dbee wrote the connections file, so changes here won't be saved." Fields a build does not know (at the top, in an entry, its tunnel, a recent entry) are kept and written back, and never reach the UI or a command's reply; the tunnel's login (`ssh.auth`) is not covered, so a field a build does not know there is dropped at a save. A command's `config` with a key the build does not know is refused (`badParams`, naming it, `ssh.auth.<key>` included), so a script's `"hots"` is not saved quietly.
- **Why:** builds of different ages share one file (a Flatpak and a package, dotfiles on two machines, a downgrade), and what the first public build does to a newer file it does for good.

## 2026-11-08: dbee's own Postgres SQL names `pg_catalog`'s functions and operators

- **Decision:** each catalog query (relations, columns, keys, the database list) runs as `SET LOCAL search_path TO pg_catalog, pg_temp; <query>` in one message, so the setting ends with that query's implicit transaction, and the queries name `pg_catalog`'s functions and tables themselves. dbee's filters, counts and saved changes name `pg_catalog`'s operators, in parentheses (`("code" OPERATOR(pg_catalog.=) CAST('a' AS pg_catalog.text))`; `in` as such equalities joined by `OR`; the patterns as `~~`, `!~~`, `~~*` and `!~~*`), where the column's operators are built in: its base type (after domains) is in `pg_catalog`, or is an array, an enum, a range or a composite (`ColumnInfo::operators`, which the catalog reads). A type whose operators are its own (an extension's: `citext`, PostGIS; or a domain over one) is compared as its base type, with the operators of its default btree operator class (strategies 1 to 5, `<>` as the `=`'s negator; `=` and `<>` from its hash class where it has no btree one), each named in its own schema, which the catalog reads: `(CAST("c" AS ext.citext) OPERATOR(ext.=) CAST('ANN' AS ext.citext))`. No operator is looked up by its name, which would find one someone made in a schema they can write (an extension lands in `public` by default, writable by everyone up to Postgres 14): a comparison the class lacks fails before anything is sent ("lquery values can't be compared with ="), and `hstore`'s "less than" is its own ordering, `#<#`. Counts are `pg_catalog.count(*)`, and the casts to text name `pg_catalog.text` (also `bpchar` and `"bit"` in filters). A type's label leaves out a schema the session's search path finds (read once at connect, `current_schemas(false)`), as Postgres shows it, in the grid, the tree and the filter bar (`ColumnInfo::label`), while `type_sql` names it for SQL. A search path that lists another schema before `pg_catalog` gets a warning at connect: the type names in casts (`jsonb`, `uuid`) are still found through it.
- **Why:** Postgres takes an operator or a function whose argument types match exactly over one that needs a coercion or is polymorphic, whatever the search path's order (the pattern of CVE-2018-1058), so one someone made in `public` runs as whoever filters or saves. Measured on both Postgres test servers with the default search path: a planted `public.unnest(smallint[])` and `name !~~ name` ran during dbee's catalog read, and planted `varchar = varchar`, `varchar = text`, `varchar <> text`, `varchar < text`, `integer[] = integer[]` and an enum's `=` ran during its filters, counts and saves; none runs now, and the primary key's index still serves each comparison (`EXPLAIN` with sequential scans off). With an extension's type in a schema after `public` on the path (as Supabase lays out its `extensions`), or a domain over one, a planted exact match in `public` won over the extension's own operator too, and naming the type's schema still let a `<` that `hstore` lacks be planted beside it in `public` (both measured on both servers); none is called now.

## 2026-11-08: MySQL's executable comments are code

- **Decision:** on MySQL and MariaDB the lexer reads `/*! … */` and `/*M! … */` (with a version or without) as code: the text inside is coloured and split as SQL, and the marks stay in the statement dbee sends, also at its end. A `*/` closes one only while one is open (`SELECT 6*/*x;SELECT 7;*/2` is one statement, as on the server), and a `;` inside an open one ends no statement.
- **What still differs from a server, measured on all five:** a `/*M! … */` is a plain comment on MySQL, and a comment whose version is above the server's is skipped by it (MariaDB also skips `/*!` with a MySQL 5.7 to 9.x version), while dbee colours and splits both as code for every server. Both differ in the safe direction: dbee shows more than the server runs, or the statement fails; it never shows as a comment what the server runs. The read-only guard does not rely on the colours: it reads each statement as its server will, refuses one whose skipped comment holds another (the server ends it at a later `*/`), and takes the server's own report of each statement (2026-11-08, read-only).
- **Why:** the server runs what such a comment holds. dbee coloured it as a comment, and cut a trailing one off before sending, while `DELETE … WHERE /*! 1 = 1 OR */ id = 2` deleted every row (measured on all five servers). The server runs what the editor shows (2026-11-06).

## 2026-11-08: Postgres values with a backslash are dollar-quoted; Apply checks client_encoding

- **Decision:** a value dbee writes into Postgres SQL that holds a `\` is written as a dollar quote whose tag occurs neither in the value nor across its end (`$v$a\b$v$`); every other value stays `'…'` with `'` doubled. Before the statements of an Apply, and again before its `COMMIT`, dbee reads `client_encoding`; when a function or a trigger changed it, dbee writes nothing (it rolls back what the Apply ran), sets it back to UTF8 and asks to apply again. A trigger that changes it for one row and sets it back before `COMMIT` is not seen: that row's value is written as other text (`Ã©` for `é`), never as other SQL, since no client encoding ends a dollar quote early (measured under eight client encodings). A statement that turns `standard_conforming_strings` off (`SET`, `RESET`, `set_config`) is refused on every connection, and before a statement whose `'…'` strings hold a backslash dbee checks it is still on; when it is not, dbee turns it on again and does not run the statement.
- **Why:** what `'…\…'` means depends on `standard_conforming_strings`, and what `E'…\\…'` means on `client_encoding` and `backslash_quote` (under SJIS the byte `\` can be the second half of a character), all of which a function the session calls, through a view say, can change. A key holding `\'` ended its literal early and the rest of it ran as SQL (measured on both servers, first with the setting, then with `E'…'` under SJIS and `backslash_quote` on). A dollar quote carries no escape, so it reads the same under all three; but under another `client_encoding` the server reads every byte above ASCII as other text, which is why Apply checks it.

## 2026-11-08: Read-only refuses what could turn it off, and checks the mode after each statement

- **Decision:** on a connection set read-only, the driver refuses, before sending, the statements that can turn read-only off or write in spite of it, and says why in plain words. On Postgres: `DO`, `CALL`, `SET` of a read-only setting to anything but one value that turns it on, `RESET` of one, a `SET` with `READ WRITE`, `BEGIN` or `START TRANSACTION … READ WRITE`, `RESET ALL`, `DISCARD ALL`, `COMMIT` or `ROLLBACK … AND CHAIN`, `set_config` of a read-only setting, the large-object functions that write (Postgres 14 runs them in a read-only transaction), `ALTER SYSTEM`, and `COPY … TO` a file or a program (the `TO` outside parentheses). On MySQL and MariaDB: `CALL`, `PREPARE`, `EXECUTE`, `SET STATEMENT`, a `SET` of the read-only variable to anything but one value that turns it on (`= 1 - 1` is refused) or with `READ WRITE`, `START TRANSACTION … READ WRITE`, `AND CHAIN`, `INTO OUTFILE` and `INTO DUMPFILE`, and `SET GLOBAL` and `SET PERSIST`; `SET NAMES`, `SET CHARACTER SET` (or `SET CHAR SET`, which the servers read as one) and `SET CHARSET`, and a `SET` of `character_set_client`, to anything but `utf8mb4`, `utf8mb3` or `utf8`; a block of several statements (one that still holds a `;` after dbee's split, which only `DELIMITER` lets through: MariaDB's `BEGIN NOT ATOMIC … END`, `IF … END IF`), as Postgres's `DO`; a `SET` with a character outside plain ASCII outside its `'…'` strings, since every system variable's name is ASCII and the server folds a name such as `sëssion_track_…` (MySQL 8.0 and later) or `ſession_track_…` (MariaDB 13) to one of them; and from the raw text, comments and strings included, a statement that names `session_track`, one that holds `SET` beside `sql_mode`, one that holds `SET` beside `NAMES`, `CHARSET`, `CHARACTER SET`, `CHAR SET` or `character_set_client` (to `utf8mb4` too: dbee sets the character set at connect), or, on MariaDB, `STATEMENT` beside the read-only variable. These raw rules find `SET` with any mark but a letter, `_` or `$` around it (the server reads those as part of a name), also right after a version comment's number (`/*!40101SET …*/`, which every server runs), so they refuse more than they need (`SET1`, a `SET` inside a string). So a read-only session reads dbee's text as it did at connect: the mode and the character set decide how the server reads quotes and bytes, and each time the session could change them, a review found a text dbee read otherwise than the server (under `sjis` or `gbk` the last byte of a character takes the `\` or backtick after it; under `ANSI_QUOTES` a `"…"` is a name). The text check reads each statement as its server will: a version comment the server skips is blanked, one that holds another comment is refused (the server ends it at a later `*/`), strings are read with backslash escapes off while the session's `sql_mode` has `NO_BACKSLASH_ESCAPES` (from the server's status flags), `"…"` as a name when the `sql_mode` read at connect has `ANSI_QUOTES`, and a line comment (`--`, MySQL's `#`) ends where the server ends it: at a line feed only on MySQL, MariaDB and SQLite, at a carriage return too on Postgres, in the check and in the query tab's split alike. Names spelled with Unicode escapes (`U&"…"`, `UESCAPE` too) are read as the names they spell. On SQLite the authorizer refuses `ATTACH` (and with it `VACUUM INTO`) and setting `query_only`, and its hint names the case that applies.
- **After each statement:** Postgres reads the mode back (both settings with `SHOW`, which takes no snapshot). MySQL and MariaDB take the server's own report: both sessions of a read-only connection track the read-only variable and the transaction's characteristics (`CLIENT_SESSION_TRACK`), so every OK packet says when a statement changed them, however its text was spelled; a server that cannot report is refused for a read-only connection. When the mode changed, the driver rolls back, turns read-only on again and says so; on MySQL and MariaDB it also sets the tracking up again, which the statement may have turned off with it. When that fails, it closes the connection. What a check cannot see right away is checked before the next statement: on Postgres a read the transaction's failure kept from running; on MySQL and MariaDB the mode after an error, which carries no report (MariaDB also drops what a statement changed before its error), read before the next statement that is not `SHOW WARNINGS`, `SHOW ERRORS` or `GET DIAGNOSTICS`, which the read would clear. A read before a statement that a cancel stopped stops the statement too, and on MySQL a read the server refused does. The connection form shows, while Read-only is ticked, that it guards against mistakes and that a database user without write rights is the lock.
- **What is guaranteed, and what is not:** every statement known to turn read-only off, or to write in spite of it, from its own text is refused before it is sent or caught right after it (tested on all five MySQL and MariaDB servers, both Postgres servers and SQLite). On MySQL and MariaDB the server's report also catches one statement whose spelling the text check misreads, while the session's tracking is on, and what `PREPARE`, `EXECUTE`, `EXECUTE IMMEDIATE`, `CALL` and a function changed (measured on all five servers); a block of several statements gets no such report and rests on the text check. A further crafted form that gets past the check is listed in gaps entry 38. What a function or a procedure does inside its one statement stays out of reach: one that writes before its statement ends, and on MySQL and MariaDB one that turns session tracking off, after which a statement that slips past the text check goes unreported too, or one that changes `sql_mode` or the character set (gaps entry 27). Read-only is not a security boundary.
- **Why:** issue #8: a pasted script (`pg_dumpall`'s starts with `SET default_transaction_read_only = off`), a `DO` block that commits, `START TRANSACTION READ WRITE` and MariaDB's `SET STATEMENT` all wrote on a read-only connection, some leaving the session looking read-only. On MySQL and MariaDB a statement could then be hidden from the text check three ways in turn (a version comment, a comment nested in a skipped one, `NO_BACKSLASH_ESCAPES`), each fix of the lexer leaving the next difference from the server; the server's report does not depend on how the text is spelled, and it ended the read after warnings and the extra round trip per statement. The report itself could then be turned off with a name the server folds to `session_track_system_variables`, and a write could happen inside a MariaDB block before the block's one report; both are refused before sending now. A block could write again after `SET NAMES sjis` had the server read as part of a character a `\` or a backtick that dbee saw on its own, and again under `ANSI_QUOTES`. Each fix had added a reading of the text; now the session cannot change how it reads text, and the guard reads it as the session does. A version comment's number glued to `SET` then hid a name outside ASCII from the raw check, and on MariaDB 13 a block wrote again; the raw rules now share one reading of `SET`. The last two were `SET CHAR SET`, and a comment that a bare carriage return ended for dbee but not for the server; both are closed.

## 2026-11-08: SQLite files open with SQLite's own hardening

- **Decision:** every SQLite file opens with `SQLITE_DBCONFIG_DEFENSIVE` on and `cell_size_check` on; an isolated run's file opens with `SQLITE_OPEN_NOFOLLOW` on the path its check resolved. `trusted_schema` stays on, SQLite's default.
- **What changes in a query tab:** `PRAGMA writable_schema = ON` no longer lets SQL write the schema (measured), and `journal_mode = OFF` and `schema_version = N` stop working, as SQLite documents for `DEFENSIVE`.
- **Why `trusted_schema` stays on:** off, it keeps a file's views, triggers and defaults from the functions and virtual tables SQLite does not mark harmless. dbee registers no SQL function and no virtual-table module, so that protects nothing today, while views over FTS's `MATCH`, `snippet()` and `bm25()` or a pragma table function failed with "unsafe use of …", in table tabs with no way around (measured with the bundled SQLite 3.53). Turn it off the day dbee registers a function or a module that has effects.
- **Why:** SQLite's advice for files from sources one does not know, which any file a file manager hands dbee can be. `NOFOLLOW` closes the race in which a link swapped in after the check opened a file outside the allowed folders (measured: won within the first tries before).

## 2026-11-08: The connections file is private

- **Decision:** where the system has file modes, the folder of `connections.json` is made `0700`, and the file, its lock and a damaged file moved aside `0600`, whatever the umask; a folder and files made before are tightened at the next write.
- **Why:** the file holds no passwords, but it lists every saved server's host, user, database, SSH host and key path, which other local users could read (`664` under a umask of `002`, measured).

## 2026-11-08: TLS follows libpq; the password goes in clear text only over TLS

- **Decision:** the SSL modes keep libpq's meaning, the standard among similar clients: `prefer` stays the default, `require` encrypts without checking the certificate (with a CA file, it checks the certificate against it, but not the name), and `verify-ca` and `verify-full` check it. There is no trust-on-first-use pinning of an unchecked certificate, and an MD5 login over a plain link is answered, as libpq answers it. On a link without TLS, direct or through the SSH tunnel, neither driver sends the password in clear text: a Postgres server's request for it (`AuthenticationCleartextPassword`) ends the login before tokio-postgres can answer, as MySQL's did already (2026-10-30). That is dbee's own refusal, not the server's: `DbError::ClearPassword` (code `clearPassword`) says dbee stopped the login and to set SSL mode to verify-full, not `require`, which without a CA file takes the same man in the middle's certificate, and the engine never turns it into a password prompt. To see that request, dbee opens the direct TCP stream itself, with tokio-postgres's socket options (`dbee_driver::tune`), and hands it and the tunnel's channel to `connect_raw` inside a watch that reads the login's messages below TLS (`crates/pg/src/watch.rs`). Over a Unix socket, which never leaves the machine and on which Postgres has no TLS, the password goes as the server asks. The cancel of a Postgres session over TLS goes over TLS or not at all, under every mode; MySQL's KILL already did.
- **Each connection of an open connection:** under `prefer` each connection negotiates TLS on its own, and the window shows the browse connection's. A query connection with less TLS than the browse connection (`TlsState`, the same mode and CA file) means someone on the network stopped it: it closes, nothing is sent, and the run fails with a message that says so and what to do. It is the one extra connection the engine opens for an open connection.
- **What the user sees:** the open connection shows its link in the status bar (`Not encrypted`; `Encrypted, server not checked`; `Encrypted, certificate checked` under `verify-ca`, or `require` with a CA file, whose hover says the name was not checked; `Encrypted, server checked` under `verify-full`), from `ServerInfo::tls`, and `tls` in the connection's summary. The hover of `Not encrypted` has its own words for a link that does not leave the machine and for one through the SSH tunnel. A `prefer` connection that ended without TLS warns, on open and on a reconnect, when its direct link reached an address on the network; not to a loopback address (127.0.0.0/8, `::1`, decided on the address the socket reached, not on the host name), from which nothing leaves the machine, nor over a Unix socket, nor through the tunnel, which encrypts the link as far as the SSH server, the rule of the server's key (2026-10-31). The form says, on the SSL mode label's row, what the chosen mode checks. Since 2026-11-11 (M3's status bar, following #9 and the quiet footer) the bar names the link only while it is weaker than fully checked: under `verify-full` it shows nothing, and the connection's `tls` still says `checked`.
- **The connect limit:** the 15 s of `CONNECT_TIMEOUT` hold for each step, as libpq's `connect_timeout` holds for each address: the TCP connection to each address in turn, or the tunnel's channel; the login; the session setup. One bound on the whole attempt had let a silent first address use up the next one's time.
- **Why:** modes that mean what libpq's mean are what people who set them expect, and pinning would bring a prompt and a stored fingerprint that libpq's users never meet. The holes that were found are closed without them: a man in the middle of a `prefer` or `disable` link had the Postgres password itself for the asking, and the cancel key of a session over TLS; he could strip TLS from the query connection alone, under a status bar that said encrypted; and nothing told the user that `prefer` had fallen back to plain text.

## 2026-11-08: The byte caps count what a kept cell holds

- **Decision:** `Limits::max_bytes` counts memory, not text: each kept cell its slot (`Option<String>`, 24 bytes) and its text as glibc's allocator holds it (`(len + 8)` rounded up to a multiple of 16, 32 at the least; no block for NULL or an empty text), each kept row its `Vec`, and each column its struct and names (`cell_cost`, `ROW_COST`, `column_cost` and `result_cost` in `dbee-driver`), on all three drivers and in a query run's budget over its statements. A server's catalog read holds the results of all its queries until it builds the catalog, so `CATALOG_LIMITS`'s 512 MiB are one budget for the whole read (`CatalogBudget`), and the database list has its own. Postgres's session setup and read-only guard read through a bounded read of a known shape (`query::own_read`: one column, 6 settings in 64 KiB, 1,024 schemas in 256 KiB, the guard's 2 values in 4 KiB); past that the connect or the statement ends in a plain error.
- **One column rule on every engine:** a column's name and type name are cut to the engine's own limit, measured on the servers: 63 bytes on Postgres, 1,024 on MySQL and MariaDB (an alias is 256 characters, up to 4 bytes each; SQLite has none). A result's columns count against what is left of `max_bytes`. When they don't fit, the driver reads and drops the rest of the answer, and the statement ends in `DbError::TooLarge` (code `tooLarge`), with the connection in step: no "connection lost" on the next statement. So once a query run's budget is spent, a statement that returns columns fails and the run ends there; a statement without columns still runs.
- **The column ceilings:** a Postgres result of more than 1,664 columns, the most a Postgres query can return (measured on both servers: "target lists can have at most 1664 entries"), is refused. MySQL and MariaDB keep their ceiling of 65,535: a `SELECT` of 70,000 columns ran on all five servers (measured), so 4,096, a table's limit, would refuse real results; a wide result is cut by the cap like any other.
- **Why:** a NULL cell counted no bytes and held 24, so the 256 MiB cap held about 15.7 GB of a hostile 65,535-column result; a short text counted 16 bytes and held 56; the catalog read, which every `connection.open` runs, held its results of up to 5 million rows each; and Postgres's setup held whatever it was sent, from the connect alone. A failed allocation aborts dbee, and the unsaved queries with it.

## 2026-11-08: Server text is cut where it is kept

- **Decision:** a server error's message is kept to 8 KiB (`MAX_MESSAGE`; on Postgres also its detail and hint, the values its session setup reads and every text taken from tokio-postgres, the SCRAM error among them), the version to 256 bytes (`MAX_VERSION`), MariaDB's type name from its extended metadata to 64 bytes, and MySQL's session-tracked database name to 256, each cut at a character boundary with `…`. Column names follow the column rule above. tokio-postgres's ParameterStatus map is out of dbee's hands (gaps entry 45).
- **Why:** a server could hand dbee an error of up to 1 GiB, a version of 256 MiB and a type name of 64 KiB per column, kept twice, none of it counted against a cap. MySQL's own messages end at 512 bytes, and no real type name comes near 64.

## 2026-11-08: The control channel takes a token and proves itself; screenshots go in one folder

- **Decision:** the channel stays TCP on `127.0.0.1`, on every system, and each start writes a token file only this user can read: two random lines of 256 bits, `0600` in a `0700` folder. A connection's first line must be the first line of the file, or it gets one `unauthorized` reply and is closed with nothing run. The reply to the right line carries the second line, which the client compares with the file before it sends anything else.
- **Not a Unix socket:** a socket in `$XDG_RUNTIME_DIR` would prove both ends as well, but Windows would still need the token, so there would be two transports, and the one Windows uses would go untested here. With one, `--control <port>`, "a port in use stops the start" and every client's first step stay the same on every system.
- **Why two lines:** the client speaks first, so a single token proves only the client: whatever holds the port learns it, and could answer with it. The second line goes out only to whoever knows the first. A stale file gets a client nothing: the next start makes new lines, and whoever holds the port now cannot give the old proof. So the file is written only after the port is taken, and a start that finds the port in use leaves the running app's file alone.
- **The first line is bounded:** 4 KiB, and 10 seconds for the whole line, so a connection that has proved nothing takes no 64 MiB buffer and does not keep one of the 16 places.
- **Known limit, not measured:** on Windows `std`'s listener does not ask for exclusive use of its port. By Microsoft's table (Winsock, `SO_REUSEADDR` and `SO_EXCLUSIVEADDRUSE`) a second bind on `127.0.0.1` is refused, for the same user too, and a bind on the wildcard address goes through and should not get `127.0.0.1`'s connections. Nobody has measured this. Asking for exclusive use takes `unsafe`, which dbee forbids. Also on Windows dbee sets no rights on the token file, which takes its folder's: under the user's profile that keeps other accounts out, and elsewhere it may not.
- **Decision:** `ui.screenshot` writes only in one folder, chosen by whoever starts the app (`DBEE_SCREENSHOT_DIR`, `target/look` in `run-isolated`, else `screenshots` in the settings folder), and `path` is a plain file name. A name with no folder in it leaves no link or `..` to meet on the way, and a `path` from before this rule fails with a clear error rather than making `target/look/target/look/`. A plain file of that name is replaced, as agents reuse names, by writing a new `0600` file and renaming it over: a link there is refused, and even one that appears after the check is replaced, never followed. In an isolated run the folder must lie in `DBEE_ALLOW_DIRS`. Without `path` the picture still comes back as base64.
- **Decision:** an isolated run's folders bind an SSH key file and a CA file too. The connect job checks them with `dbee_driver::allowed_file` before it opens anything, so "the engine checks only what needs no filesystem read" (2026-11-03) still holds for the UI thread. A CA file is checked whatever the TLS mode, even under one that does not read it: the rule stays right if a mode's reading changes.
- **Why:** issue #10: any local process could drive a dbee started with `--control` and reach every saved connection with its stored password, whoever bound the port first received an agent's requests, and `ui.screenshot` could overwrite any of the user's files, even in an isolated run.

## 2026-11-08: A stored secret is kept with the settings it was saved for

- **Decision:** each value in the secret store holds the secret and the settings it was saved for: `{"v":1,"secret":…,"for":{kind, host, port, user, sslMode, caFile, ssh, weakening}}`. The connect job compares those with the settings it is about to use, at the read (`reuse`), and neither the connections file nor a window's copy of it has a say. A window that holds old settings, a rewritten file and a move between the file's lock and the keyring write each end in a password prompt, not in the password going to another server. The entry names stay as they were: a hash of the settings in the name, the other way to bind them, could not say "TLS at least as strong".
- **The database password needs:** the same database type, host, port and user; the same tunnel (none on either side, or the same SSH host and port); TLS at least as strong; the same CA file where either side checks the certificate with one; and no option on that protects it less. `require` with a CA file ranks with `verify-ca`, because it checks what `verify-ca` checks. The SSH password and the passphrase keep their rules: the same SSH host, port and user, and for the passphrase the same key file.
- **A save moves what it keeps:** a secret the new settings still allow is stored again for them, so going from `require` to `verify-full` leaves nothing for a window that still says `require`. A save with no such setting changed, a new name or another database for example, does not touch the store.
- **The database does not count:** it is not kept with the secret and not compared. The password goes to the same server and the same user whichever database the settings name, so comparing it would add no protection, and other database clients don't ask either. Another database in a saved connection's form, saved or not, and List… on it use the stored password without asking, and a password typed there is kept for the saved connection like any other.
- **An older build's password:** a value with no settings is used once, where the saved connection allows it as it did then, and is stored again with the saved connection's settings. There is no other migration. Until that first use it is as exposed as it was. A password can be any text, so a value counts as the new form only as an object with `v`, `secret` and `for`; one of a later form, or with settings this build can't read, is never sent as a password.
- **Known limits, not measured:** an older build sends a stored value whole, the password and its settings, as its password to the server its file names, and its login fails until the password is typed again. Windows Credential Manager holds 2560 bytes of UTF-16: a secret and its settings past about 1280 characters are refused, the user is told, and dbee asks each time.
- **Why:** the entry's name and a window's copy of the settings were all that said where a password belonged, so a second window or any program that rewrote the connections file could send it to another server; on macOS that got around the keychain's per-app check. Under `require` a password saved with a CA file also went to a link without one, and a password saved for MySQL went to the same settings named Postgres.

## 2026-11-08: Host keys are read by dbee, and a key of another type is refused

- **Decision:** `crates/ssh/src/known_hosts.rs` reads `known_hosts` itself, as OpenSSH does: fields split on spaces and tabs, `@revoked` (refused) and `@cert-authority` (no host key), comma lists with `!`, the wildcards `*` and `?`, hashed names and names without regard to case. A server whose key type is not among those recorded for it, while others are, is refused (`hostKeyOtherType`, never overridable) with the types on record; dbee asks for the recorded type first, so only a server that cannot show it, or a man in the middle, lands here. A user whose server changed its key type removes the old line from `known_hosts`. A host name goes into `known_hosts` only as letters, digits, `-`, `.`, `_` or an IP address (`ConnectionConfig::validate`, for the SSH host and the database host), so a name cannot vouch for others or add lines.
- **The database host is wider than the SSH host:** only the SSH host goes into `known_hosts`, so the database host may also be an IPv6 address with a zone (`fe80::1%eth0`, which the drivers' name lookup takes) and, for a type whose `KindInfo` says it takes a Unix socket (`Settings::Server { socket: true }`, Postgres), the full path of the socket folder, without a tunnel. A folder never reaches `known_hosts`.
- **Why:** russh's reader skipped tab-separated and `@revoked` lines, which turned a refusal into a prompt, and a key of another type read as "dbee has not connected before", which a user who knows dbee is new to them answers with Trust.

## 2026-11-08: What the journal, the replies and the log keep

- **Decision:** the journal leaves out `trustHostKey` as well as the secret params, so a replay on another machine asks about an unknown host key again. `connection.parseUrl` answers `passwordGiven`, not the password; the Fill from URL dialog reads the password from the URL it holds. The log names the host and port of the database or SSH server a connection reaches (it helps with a bug report), never params, secrets, SQL or values. The log folder is 0700 and the files 0600 where the OS has modes. A record of a crate other than dbee's own is written on one line with control characters escaped, cut at 1,024 characters, and a run writes at most 2,000 of them, because an SSH server decides some of what russh logs.
- **Why:** a journal replayed elsewhere should not trust a host key that machine never saw, a reply should not hand a password back, and what a server can make another crate log should neither fill the log nor forge its lines.

## 2026-11-23: The update check is one GET of the release's checksum file, with ureq on rustls, ring and the OS verifier

- **Decision:** dbee learns of a newer release from `https://github.com/<owner>/<name>/releases/latest/download/SHA256SUMS.txt`, GitHub's own redirect to the newest release that is not a pre-release: one HTTPS GET, no API and no JSON. The file's names carry the version (`dbee-<version>-<platform>-<arch>.<ext>`), and it is read as hostile input: at most 64 KiB and 256 lines, each a checksum and an asset name, all of one version, none twice. Every URL dbee uses is built from a template in `crates/update/src/fetch.rs`; none is read from an answer. The request carries `User-Agent: dbee/<version>` and nothing else of dbee's, is HTTPS on every hop of a redirect, takes at most 5 s to connect and 15 s in all, and reads at most 64 KiB. The repository is `KasparRosin/dbee` unless `GITHUB_REPOSITORY` named another when the binary was built, so a fork's releases check the fork's. The client is `ureq` 3.5 (MIT OR Apache-2.0) with default features off and `rustls-no-provider` and `platform-verifier` on: dbee hands it `rustls`'s ring provider, and certificates are checked by `rustls-platform-verifier`, both already in the tree. It adds `ureq-proto`, `http`, `httparse`, `base64` and `utf8-zero`. `ureq` blocks, so the check runs on a blocking thread of the engine's job runtime. A proxy the environment names (`ALL_PROXY`, `HTTPS_PROXY`, `HTTP_PROXY`, with `NO_PROXY`) is used, as `ureq` reads them; the TLS session is still with GitHub and checked as above.
- **Why:** the checksum file is in every release already, GitHub's `latest` skips pre-releases and drafts by itself, and a plain file needs no token, has no rate limit worth the name and nothing to parse but lines. `ureq`'s default features would bring `webpki-roots`, and its other TLS choices `native-tls` (OpenSSL) or `aws-lc`, all forbidden; with these two features `cargo tree -i` finds none of them, on any target (measured 2026-11-23). An async client (`reqwest`, `hyper` with its connector) is several times the dependencies for one request a day.
- **When it runs:** five seconds after the start and every 24 hours while the app is open; the answer is kept in the settings folder and a start within six hours of it asks nobody. It is off with `"checkForUpdates": false` in `settings.json` (`app.setUpdateCheck`), with `DBEE_NO_UPDATE_CHECK=1`, in an isolated run, with `DBEE_NO_PREFS`, in a development build and in every test. A failed automatic check says nothing.
- **What it tells GitHub:** the machine's address, as any request does, and `dbee/<version>`. No id, no cookie, nothing about the machine or its databases.

## 2026-11-23: Releases will be signed with ed25519 over the checksum file; dbee installs nothing without it

- **Decision:** before dbee installs a release itself, it checks a detached ed25519 signature (RFC 8032) over the exact bytes of `SHA256SUMS.txt` against a list of public keys compiled into the binary, then the downloaded file's SHA-256 against its line in that file. The signature is the 64 raw bytes. A release signed with any key of the list is accepted, so a key can be replaced over two releases, for the copies that take the release between them. The check is `dbee_update::verify`, on `ring` (already in the tree), tested with a test key: a good signature, a changed file, a changed signature, another key, a truncated one, no key.
- **Not yet (as of 2026-11-23; see 2026-11-24 for the key):** no key is compiled in (`PINNED_KEYS` is empty, so nothing verifies), the release workflow signs nothing, and where the private key lives is not decided. Nothing is installed until then: every copy's button opens the release's page, where the browser and the system's own checks apply.
- **Why:** the release's files are served by GitHub, and TLS says only that GitHub served them. A signature made outside GitHub means that an account or a workflow taken over cannot hand a running dbee, which may hold database passwords, a binary to run. One signature over the checksum file covers every asset, and ed25519 needs no new crate. (Changed on 2026-11-24: the key is a CI secret, so the signature is made inside GitHub; see that entry for what it still covers.)

## 2026-11-23: Each package says how it was installed in a one-word marker file

- **Decision:** the app finds how it was installed in this order: Flatpak (`/.flatpak-info` exists), AppImage (`$APPIMAGE` is set), a marker file holding one word, then a macOS app bundle whose `Info.plist` gives the bundle id `dev.rosin.dbee`, else unknown. The marker is `share/dbee/install-kind` beside the binary's `bin/` on Linux and FreeBSD (`/usr/share/dbee/install-kind` for a package) and `install-kind` beside `dbee.exe` on Windows; the words are `deb`, `rpm`, `tar`, `msi` and `portable`. The packaging writes it: nfpm's per-packager `contents` for the `.deb` and the `.rpm`, the tarball's own tree (never the tree the AppImage shares; the Flatpak is built from the tarball without it), a component beside `dbee.exe` in the MSI, and the portable zip's folder. The scripts read it back from each package they build, and `packaging/check-install-kind.sh`, run by the packaging lint, checks that each format writes its own and the others none.
- **Why:** the same binary goes into every Linux package, so it cannot know from itself whether apt, dnf or nobody owns it; asking `dpkg -S` or `rpm -qf` at run time is slow, differs per distribution and says nothing for a tarball. A file the package owns is removed and replaced with it, and a copy built from source or packaged by a distribution has none and is offered the download page, never an install it could not finish.

## 2026-11-24: The release key is a secret of the `release` environment

- **Decision:** the private half of the release key is the secret `RELEASE_SIGNING_KEY` of the repository's `release` environment, an ed25519 key in PEM (PKCS#8). The last job of the release workflow signs `SHA256SUMS.txt` with it (`openssl pkeyutl -sign -rawin`) into `SHA256SUMS.txt.sig`, the 64 raw bytes, and then runs `dbee_update::check_release` on the files (`crates/update/examples/check_release.rs`): the checksum file must read as a manifest, and once a key is pinned in `PINNED_KEYS`, a release without a signature by it is not drafted. [`releasing.md`](releasing.md) says how the key is made. This replaces "the release workflow signs nothing, and where the private key lives is not decided" in the entry of 2026-11-23.
- **What it covers:** the signature is made in the workflow, so it no longer stands outside GitHub, as the entry of 2026-11-23 gave as its reason. It still holds against a release's files being changed after the workflow ran, by hand or with a token that can write releases but not run the `release` environment, and against a file changed on its way to the user. It does not hold against whoever can push to the `release` branch or change what runs in that environment: they can have anything signed, and can copy the key out. A copied key cannot be called back: the copies in use accept what it signs until each is updated, by hand, to a release that no longer pins it. The owner's GitHub account and the `release` branch's protection are therefore what a copy that installs by itself trusts.
- **Why:** a release needs no step on the owner's machine and no key to keep and carry; a key kept offline was the other choice.
- **State, 2026-11-25:** the key exists: the secret is set, its public half is in `PINNED_KEYS`, the `release` environment deploys from the `release` branch only, and that branch refuses deletion and force pushes. No release is signed yet, the signing step has not run on GitHub, and nothing installs: from the next release on, the workflow refuses to draft one without a signature by this key.

## 2026-11-25: A query result sorts in memory, among the rows held

- **Decision:** a click on a column header of a query tab's result sorts that result by the column (asc, desc, then the order the server sent), as a table tab's header does, through a command of its own, `query.sortResult {column, dir?}`. The sort is done in dbee, over the rows the result holds: it sends nothing to the database, needs no connection and starts no job. The rows are not moved or copied: the result keeps a list of row indices beside them (`StatementOutcome`, `crates/engine/src/state.rs`), which the grid, every copy and the value panel read through, and dropping the sort drops the list. One column at a time, named by its 0-based index (a result's columns can share a name or have none). Each result of a run keeps its own sort; a new run replaces the results and with them every sort; the selection stays at its place in the grid. The command is not journaled (a replay has no result to sort) and not undoable (undo is for staged edits; a third click gives the received order back).
- **Why not `ORDER BY`:** a table tab sorts in the database (`table.sort` asks for a page in that order), because it shows 100 rows of a table of any size. A query result is the answer to a statement the user wrote. Wrapping that statement in `SELECT … ORDER BY` would run it again (its side effects, another snapshot, its time, a live connection and a healthy transaction needed), cannot wrap what returns rows without being a query (`INSERT … RETURNING`, `EXPLAIN`, `SHOW`, `PRAGMA`, `CALL`), and would still bring back only the first 10,000 rows. The result is in memory already, at most 10,000 rows.
- **Among the rows held:** a result the cap cut (`First 10,000 of 25,000 rows`) sorts the 10,000 rows loaded, not the statement's rows: the smallest value in the database may not be among them. The header's hover says so with the count of the rows held, `Sort the <n> rows loaded by this column` (`Sort the 10,000 rows loaded by this column` at the row cap, `Sort the 1 row loaded by this column` for one), and the bar keeps its notice.
- **How cells compare** (`dbee_core::sort`): a cell is the server's printed text and its column a class, so the order is by three rules, each in one place.
  - NULL sorts where the connection's database puts it (`Dialect::nulls`): after every value ascending on PostgreSQL, before every value ascending on MySQL, MariaDB and SQLite, and at the other end descending. Checked against each test server's own `ORDER BY` (`sort_result_nulls_as_the_engine_sorts_them`).
  - A number column compares by value, exactly, from the digits (sign, digits, exponent; never through a float), so a 64-bit integer past 2^53 and a long decimal are right and `1`, `1.0` and `1e0` are equal; `NaN` sorts above `Infinity`. A cell of a column the engine names no type for (SQLite's expressions: `count(*)`) that reads as a number compares as one, so `9` comes before `10` there too, and so does a boolean column's cell (MySQL's and MariaDB's `TINYINT(1)` is their boolean and holds any small integer; `f`, `false` and `0` come before `t`, `true` and `1`). What is no number comes after every number, as text; so does a cell longer than 1,024 bytes, whatever it holds. With an exponent at an end of a 64-bit integer's range, or within the cell's length of it (`1e9223372036854775807`, `9e9223372036854775806`), numbers compare by a rule, their digits, not by value: no engine prints such a number, and the order stays total.
  - Everything else compares as text: without regard to case first (each character's Unicode lowercase, over the first 256 characters), then by bytes: `Apple, apple, fig, Zucchini`. A text's first 256 characters are folded once, by the first comparison that needs them (one with a text that differs from it in case where the two first differ), and kept while the sort runs. Dates and times sort right as text in the ISO forms the servers print.
  - Rows that compare equal keep the order the server sent, ascending and descending alike.
- **Where the order differs from the database's.** dbee knows no collation and no type's own comparison, so a column can sort differently in a query tab than under `ORDER BY`, or in a table tab. Known cases, from the engines' documentation and from how the comparison is written. None of them was run against a server by a test; one was seen by hand, once ([gaps.md](gaps.md) 89: SQLite's text from a table tab's header and from a query tab's). What was compared with each test server's own `ORDER BY` is NULL placement, among three small integers, and on MySQL and MariaDB a `TINYINT(1)` column of seven values:
  - text under a collation: a locale's order on PostgreSQL (accents, punctuation), MySQL's and MariaDB's `_ci` and accent-insensitive collations, a `NOCASE` or custom collation on SQLite. SQLite's default and PostgreSQL's `C` are bytewise, where dbee's ignores case first;
  - an enum, which the database sorts by the order its labels were declared in (PostgreSQL's enums, MySQL's and MariaDB's `ENUM`; their `SET` by its members' bits), and dbee by their text;
  - intervals, a MySQL `TIME` past 99 hours or below zero, dates before the common era or past the year 9999, `infinity` in a date column, and times with differing time zone offsets, which sort as text;
  - numbers a type prints with more than digits (PostgreSQL's `money`), which sort as text;
  - a column the engine names no type for, or one dbee does not class (on PostgreSQL bit strings, arrays, `uuid` and others), whose text reads as a number: it sorts as a number, so `007` ties with `7`, `1e3` equals `1000`, and codes of digits come before words, where the database compares the text;
  - texts that are the same in their first 256 characters, or the same there but for case, which are in the byte order of the whole text: past the 256th character case counts, and a difference in case before it decides before anything after it does (the bound keeps what a sort folds and holds short: with no bound and every comparison folding both of its texts, as the comparison first was, sorting 10,000 values of 20 kB that differ only in case took 23 s on 2026-11-25 and 25.6 s on 2026-11-26, in the frame of the click; the second measured on the machine named under "Cost" below at a load average of 0.88 / 1.93 / 1.88).
- **Three rules that may change:** NULL placement following the database (the other choice: always last), text ignoring case first (the other: bytes alone, which is SQLite's and PostgreSQL `C`'s own order), and a cut result sorting at all (the other: off, with the reason on hover). Each is one rule in the code: `Dialect::nulls`, `dbee_core::sort::text_cmp` (its `Text`: the key and the comparison), and `can_sort_result` with `sort_hint`.
- **Not decided here:** export. File export is M4; whether an exported query result follows the sort shown is open. Nothing is claimed about what Beekeeper Studio does on a result header click: it was not observed.
- **Cost:** `dbee_core::sort::order` over 10,000 rows, which runs in the frame of the click, took 1.8 ms for numbers, 5.6 ms for short texts, 7.5 ms for 10,000 copies of one 20 kB text and 20 ms for numbers of 1,000 digits that differ at their end. The worst cases found are long values that are alike nearly to their end. The worst of them, 0.31 s, is texts of 26.8 kB that fill a run's 256 MiB and differ at their end, their first 256 characters of four bytes each. The others took 0.15 to 0.18 s: 160 ms for texts of 20 kB that differ in case at their first character, 151 ms for texts of 20 kB that differ at their end, and 178–179 ms for digit strings of 25,000 (that differ at their end, or after 25,000 zeros before the number or after its point; past 1,024 bytes a cell is text, not a number). Texts that are the same over their first 256 characters but for case, each letter in a case of its own, took 36 ms (ASCII letters) and 81 ms (Cyrillic): a text's first 256 characters are folded once and kept while the sort runs. With every comparison folding both of its texts, as the comparison first was, the same two took 559 ms and 1.81 s (the same build but for that, at a load average of 0.64 / 1.22 / 1.74). The kept key has a cost of its own where none was needed: texts of 256 Cyrillic letters that differ in case at their first letter and by more right after took 51 ms, and 12 ms when two letters were folded at each comparison. Medians of 5, targets 16 ms for the first three, 100 ms for the long numbers and for those last texts, and 500 ms for the rest; measured 2026-11-26 on an Intel Core i5-14400F (16 threads) in the dev container, dev profile, at a load average of 0.50 / 0.65 / 1.44, with `a_sort_of_ten_thousand_rows_within_a_frame` (`crates/core/src/sort.rs`, `#[ignore]`). The command and the frame around it were timed once, by hand, in the real window on PostgreSQL: `query.sortResult` over the control channel answered in 90–97 ms on 10,000 of those Cyrillic texts.

## 2026-11-26: A page opens through the desktop's opener, not a library

- **Decision:** the update button's page is opened by starting the system's own opener with the address as its one argument, through no shell: `xdg-open` on Linux and FreeBSD, found on `PATH` (inside a Flatpak it asks the desktop's portal), `/usr/bin/open` on macOS, `rundll32 url.dll,FileProtocolHandler` on Windows (`crates/ui-egui/src/browser.rs`). The real app installs that browser (`DbeeApp::with_browser`); a window without one, and one that keeps its clipboard in memory, opens nothing.
- **Why not egui's:** `Context::open_url` opens a page only where eframe is built with its `links` feature, which brings the `webbrowser` and `url` crates and the Unicode tables behind them, 28 more crates in `Cargo.lock` (counted 2026-11-26), and a page that does not open there is one line in the log. dbee was built without the feature and no test saw it, so 0.3.1 and 0.3.2 show `DOWNLOAD <version>` and a click on it opens nothing: the tests then read the page the app asked for, not whether anything was started.
- **What the opener is handed, and where:** only `https://` followed by ASCII letters, digits and `-`, `.`, `_`, `/`, which is what a release's page is made of; any other address is refused. So a version with build metadata (`0.3.3+words`), which the manifest's reader lets through and no release of dbee's carries, has no page dbee opens. On Linux, FreeBSD and macOS the opener is started in `/`, not in the folder dbee was started in: some openers (KDE's; perhaps macOS's `open`) take a file there of the address's own name for what to open. This is from how those openers are described, not from a run. Windows needs none of it, where no file can have such a name. On those three the opener is also in a process group of its own, so what ends dbee from its terminal does not end a browser the opener stayed with.
- **A click that opens nothing says so:** an opener that does not start, or that ends in failure within 3 s of its start, shows a notice with the reason and the page's address, and puts the address on the clipboard, since a notice's text cannot be copied. A later failure is only logged, and so is one whose frame comes more than 3 s after it was told (a window that was minimized): some openers stay for as long as the browser they started, and the clipboard may hold something newer by then.
- **The packages:** the `.deb` and the `.rpm` recommend `xdg-utils`, which brings `xdg-open`.
- **Checked:** on Linux, in the real window with a stand-in `xdg-open` as the app's whole `PATH`: it is started in `/` with the release's page as its one argument (`a_click_on_the_real_apps_button_starts_the_desktops_opener_with_the_page`, `apps/dbee/tests/update_check.rs`), and that test fails when the app has no browser installed. What was not run: [gaps.md](gaps.md), entry 59.
