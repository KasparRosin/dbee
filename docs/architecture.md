# Architecture

> **Last reviewed:** 2026-10-31 · **Last updated:** 2026-11-05 · **Change:** minor (`connection.listDatabases`, the driver's database list)

How dbee is built, and how it will be built. Rules for contributors are in [`AGENTS.md`](../AGENTS.md). Anything not yet built is marked **(planned)**.

## Workspace

An engine-first Cargo workspace. Layering is enforced by `cargo xtask layers`; nothing below L6 depends on egui, eframe, winit, rfd or wgpu, so the UI crate is swappable.

Cells, result sets, the schema model (`Catalog`, `TableInfo`, row keys, table filtering), grid text, the clipboard copy formats (TSV, CSV, JSON, Markdown) and JSON: classify, validate, pretty-print and highlight, all iterative. Plain values with serde shapes; no I/O. |

Every length a server sends is checked before it is used. `MySqlDriver` serves MySQL and MariaDB behind the `Driver` and `Connection` traits. |
| `crates/sqlite` | exists | L4. The SQLite driver (`SqliteDriver`, on `rusqlite` with the SQLite library compiled in): the file opened read-write or read-only (then also `query_only`), by its absolute path so a `file:` name is never a URI, made only when asked; a path that is no regular file refused; foreign keys on, a 5 s busy timeout and a read of `sqlite_schema`, so a file that is not a database is a connect error naming it; a file the system lets it only read is read-only; the open bounded by the 15 s connect timeout. The file is closed on a blocking thread, never on the thread that drops the connection. Every call runs on a blocking thread, one operation at a time; cancel is SQLite's interrupt, sent only while a call runs, so it never reaches a later one. `run` prepares and steps each statement in turn, within the row and byte caps, refuses text with a NUL (SQLite would end the statement there) and parameters; values become text by fixed rules (reals as SQLite's own `CAST(x AS TEXT)` prints them, blobs as `X'…'`, invalid UTF-8 replaced and counted); a column's class comes from its declared type by SQLite's affinity rules, in one function the catalog uses too; a result is refused, naming the table, while a schema holds a name or type that is not UTF-8, as rusqlite cannot read them (checked again only when a database or a schema changes). One table of the result codes dbee acts on; a syntax error's offset becomes a character position. The catalog: `main`'s tables and views from `sqlite_schema` (no `sqlite_%` tables), columns, keys (`UNIQUE` constraints, not unique indexes) and foreign keys (resolved as SQLite does) from the pragmas, estimates from `sqlite_stat1`; an ordinary table without a primary key or a NOT NULL unique key is keyed by its rowid, a hidden leading column named `rowid`, `_rowid_` or `oid` (the first no column takes), and a virtual table, or one whose columns take all three names, says why it takes no edits. With `Target::allowed_dirs` (an isolated run) the open checks the file and opens the path it resolved, and an authorizer refuses every `ATTACH`, and so `VACUUM INTO` and `VACUUM`, which attach a file, and the pragmas that move SQLite's temporary files. The shared all-or-nothing apply with `BEGIN IMMEDIATE`, and a rollback step that sends no `ROLLBACK` when SQLite already ended the transaction. |
| `crates/drivers` | exists | L4. `all()`: the one list of the drivers dbee ships (Postgres, MySQL and MariaDB, SQLite). Only the apps and test code depend on it; the app passes it to the session (`SessionOptions::drivers`). |
| `crates/engine` | exists | L5. `Session`: the session state (`state.rs`; the open connection's `ServerInfo` and dialect, its connections as `Arc<dyn Connection>` from the session's driver for the database type), the command registry (`cmd/*`: tabs, connection, schema, table, edit, query, selection), background jobs on a tokio runtime (`jobs.rs`), the panic guard and the journal; staged edits with undo and redo (`edits.rs`), the quick search's scoring (`fuzzy.rs`), the grid a selection addresses and the value view (`view.rs`), and an isolated run's allowed targets (`allowed.rs`: a server's target and any SSH server's; a file's folder is its driver's to check, in the open). | `crates/ui-egui` | exists | L6. | `crates/mcp` | exists, empty | L6. MCP server over stdio. |
| `apps/dbee` | exists | L7. ## Layers

| Layer | Crates | Job |
|---|---|---|
| L0–L4 | `core`, `testkit` (L0, tests only); `sql`, `config` (L1); `ssh` (L2); `driver` (L3); the drivers `pg`, `mysql` and `sqlite`, and their registry `drivers` (L4) | Values and types, SQL parsing and quoting, the driver interface, database drivers and wire protocols, the connection and schema model. No UI, no engine. |
| L5 | `engine` | Session, commands, undo, journal. Depends on L0–L4 only. |
| L6 | `ui-egui`, `mcp` | Front ends over the engine. egui and friends are allowed here and above (`ui-egui` for the UI, `mcp` for UI control), never below. |
| L7 | `apps/dbee`, `apps/dbee-cli` | Binaries that wire a front end to the engine. |
| — | `xtask` | Build tooling (exempt). |

A crate may depend only on lower layers. Two rules for the drivers: `drivers` may use every driver, and no driver uses another or the registry; the engine and the front ends (L5, L6) may take a driver or `drivers` only as a dev-dependency, so they know drivers through `driver`'s interface alone (until M2.8 the engine still uses `pg` directly, listed as an exception in `xtask/src/layers.rs`). A driver is registered as one `Class::Driver` line, which both rules then cover. Register every new crate in `xtask/src/layers.rs` and in this table in the same change.

## Data flow

1. **Every action is a command.** The UI, CLI, control channel and MCP all call `app.run(id, params)`, which reaches `Session::execute`. A command (`crates/engine/src/cmd/*`, one `SPECS` table per module) has an id, label, menu path, shortcut text, params doc, `enabled` and `run`. Ids follow Beekeeper Studio's menus plus primitives (`connection.open`, `query.run`, `table.open`). UI-only commands live in `ui-egui`.
2. **Execute.** Errors carry a stable `code()` and JSON `data()`; a command that needs an answer (a password, a host key, a confirmation) returns a `needs…` error and is run again with it. `Session::execute(id, params)`:
   1. finds the command (`unknownCommand`) and checks `enabled` (`disabled`, with the reason);
   2. checks that params is a JSON object (`null` counts as `{}`); the `cmd::p` helpers check each key (`badParams` naming it);
   3. snapshots the session state, a cheap clone (large data sits behind `Arc`), and runs the command under `catch_unwind`. A panic restores the snapshot and returns `internal`, and jobs the command started are orphaned: they run to their end and their results are dropped ([never crash](standards/never-crash.md));
   4. records a successful journaled command in the **journal**.
3. **Jobs.** A command either finishes (`Outcome::Done`) or starts a job (`Outcome::Started`). Jobs are futures on the session's tokio runtime (2 worker threads named `dbee-db`). A job's future ends in an `Apply` closure; `Session::pump`, which the UI calls every frame, runs each `Apply` on the UI thread under the same panic guard, so the window never waits on the database. `wait`, `wait_idle` and `run_blocking` serve tests and the control channel. `notify` (the UI's repaint request) is called after each result. A job is never aborted: it runs to its end, a Postgres apply is never abandoned mid-transaction, and database work is stopped through the Postgres cancel request. A result whose tab has gone is ignored. Dropping the session shuts the runtime down without waiting (safe in async code too); jobs still running are dropped with it.
4. **Journal.** Successful journaled commands with their params, in memory and replayable; the localhost control channel serves it (`engine.journal`). Secret params (`password`, `passphrase`, and keys ending in `Password` or `Passphrase`) are left out at any depth. It keeps the newest 10,000 entries at most (it drops the oldest 5,000), and consecutive `query.setText` entries replace each other, as do consecutive `table.setFilters` entries with `apply: false` and the same keys (typing in the filter bar). Logs carry command ids, job labels, error codes and timings only: never params, secrets, cell values or SQL text.
5. **Connections.** `connection.open`, `connection.test` and `connection.reconnect` are jobs: the SSH tunnel, the browse connection and (for open and reconnect) the catalog, whose load is bounded at 60 s. `connection.listDatabases` is one too, for the form's Database field: the tunnel, then the driver's `list_databases`, which opens a connection of its own, reads the server's databases and closes it (bounded at the 15 s connect plus 60 s); a file type's driver lists none, and the command refuses a file type. They connect through the session's driver for the config's database type (`SessionOptions::drivers`), and a type without one is refused (`disabled`) before any job starts; the engine then holds each connection as `Arc<dyn Connection>` and builds and splits SQL in its dialect. Secrets come from the params, then the secret store, then nowhere; the store keeps them for saved connections only, and a stored secret is used only where it was saved for: the database password for the same host, port and user, the same tunnel (none on either side, or the same SSH host and port) and a TLS mode at least as strong (disable < prefer < require < verify-ca < verify-full); the SSH password for the same SSH host, port and user; the key passphrase for those and the same key file. Saving new settings forgets the stored secrets they no longer apply to, unless the save gives them again. The ones a connect used stay in memory, in crate-private fields, for reconnects. Unknown host keys, key passphrases, the SSH password and a missing database password come back as `needs…` errors. `createFile` lets a file driver make a missing database file (not for a read-only connection; an isolated run only in its folders). A browse operation that finds the connection gone marks the session `lost`, and commands that need the database are disabled ("connection lost — reconnect") until a reconnect replaces the connections, keeping the tabs. `connection.close` cancels running statements through the Postgres cancel request and lets the connections go; a job whose connection or tab went away meanwhile is ignored (`{"ignored": true}`).
6. **Tables, edits and queries.** A connection has two Postgres sessions through the same tunnel: the browse connection for the catalog, table pages, counts and Apply, and a query connection, opened on the first query run, for query tabs (one run at a time; Cancel sends the Postgres cancel request). A table page is `SELECT … LIMIT 101 OFFSET …`, ordered by the chosen sort, then the row key; filters and values go in as quoted literals with casts. Staged edits stay in the tab until Apply writes them all in one transaction, or none; a failed Apply marks the row and keeps the edits. A query run keeps at most 10,000 rows per result and 256 MiB of cell text. Results land in the tab that asked; a result whose tab or connection has gone is ignored.
7. **The UI is thin.** Panels read `Session::state()` and act only through commands. `Session::inspect()` is the JSON summary agents read (`document.inspect`).
8. **Programmatic calls never open dialogs.** Only menu-style invocation opens a dialog (`UiRequest::Dialog`, collected with `take_ui_requests`).

## Agent control

- Control channel: `dbee --control <port>`, JSON lines on `127.0.0.1`: [`control-protocol.md`](control-protocol.md). `cargo xtask run-isolated` runs the app with it on a throwaway home.
- CLI **(planned)**: [`cli.md`](cli.md).
- MCP **(planned)**: `dbee-cli mcp`, headless or bridged to a running app: [`mcp.md`](mcp.md).

## Platforms

Desktop only: macOS, Windows, Linux and FreeBSD, of which only Linux x86_64 has been built and run so far ([`hardware-parity.md`](hardware-parity.md)). There is no web build and no wasm target, because a browser cannot open database connections. See [`releasing.md`](releasing.md) for the platform matrix and [`decisions.md`](decisions.md).

## Known gaps

M1's crates are all in place. The driver interface exists, and the engine and the UI reach databases only through it. Postgres, MySQL and MariaDB, and SQLite sit behind it and are registered in `drivers`, and the connection screen offers each of them. The MCP crate is empty, and the CLI prints its version. The ranked work list is [`gaps.md`](gaps.md).
