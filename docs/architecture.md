## Workspace

An engine-first Cargo workspace. Layering is enforced by `cargo xtask layers`; nothing below L6 depends on egui, eframe, winit, rfd or wgpu, so the UI crate is swappable.

## Layers

| Layer | Crates | Job |
|---|---|---|
| L0–L4 | `core`, `testkit` (L0, tests only); `sql`, `config` (L1); `ssh` (L2); `driver` (L3); the drivers `pg`, `mysql` and `sqlite`, and their registry `drivers` (L4) | Values and types, SQL parsing and quoting, the driver interface, database drivers and wire protocols, the connection and schema model. No UI, no engine. |
| L5 | `engine` | Session, commands, undo, journal. Depends on L0–L4 only. |
| L6 | `ui-egui`, `mcp` | Front ends over the engine. egui and friends are allowed here and above (`ui-egui` for the UI, `mcp` for UI control), never below. |
| L7 | `apps/dbee`, `apps/dbee-cli` | Binaries that wire a front end to the engine. |
| — | `xtask` | Build tooling (exempt). |

A crate may depend only on lower layers. Two rules for the drivers: `drivers` may use every driver, and no driver uses another or the registry; the engine and the front ends (L5, L6) may take a driver or `drivers` only as a dev-dependency, so they know drivers through `driver`'s interface alone. A driver is registered as one `Class::Driver` line, which both rules then cover. Register every new crate in `xtask/src/layers.rs` and in this table in the same change.

## Data flow

1. **Every action is a command.** The UI, CLI, control channel and MCP all call `app.run(id, params)`, which reaches `Session::execute`. A command (`crates/engine/src/cmd/*`, one `SPECS` table per module) has an id, label, menu path, shortcut text, params doc, `enabled` and `run`. Ids follow Beekeeper Studio's menus plus primitives (`connection.open`, `query.run`, `table.open`). UI-only commands live in `ui-egui`.
2. **Execute.** Errors carry a stable `code()` and JSON `data()`; a command that needs an answer (a password, a host key, a confirmation) returns a `needs…` error and is run again with it. `Session::execute(id, params)`:
   1. finds the command (`unknownCommand`) and checks `enabled` (`disabled`, with the reason);
   2. checks that params is a JSON object (`null` counts as `{}`); the `cmd::p` helpers check each key (`badParams` naming it);
   3. snapshots the session state, a cheap clone (large data sits behind `Arc`), and runs the command under `catch_unwind`. A panic restores the snapshot and returns `internal`, and jobs the command started are orphaned: they run to their end and their results are dropped ([never crash](standards/never-crash.md));
   4. records a successful journaled command in the **journal**.
3. **Jobs.** A command either finishes (`Outcome::Done`) or starts a job (`Outcome::Started`). Jobs are futures on the session's tokio runtime (2 worker threads named `dbee-db`). A job's future ends in an `Apply` closure; `Session::pump`, which the UI calls every frame, runs each `Apply` on the UI thread under the same panic guard, so the window never waits on the database. `wait`, `wait_idle` and `run_blocking` serve tests and the control channel. `notify` (the UI's repaint request) is called after each result. A job is never aborted: it runs to its end, an apply is never abandoned mid-transaction, and database work is stopped through the driver's cancel (Postgres's cancel request, MySQL's `KILL QUERY` over a second connection, SQLite's interrupt). A query run, a page load and a count are stopped through their `Stop`: the job sends the cancel itself, and again after 1 s and then every 2 s while its statement has not ended (a cancel that reaches the server before the statement does is lost), waits for each request to arrive before it sends the next or goes on, and starts no further statement. The drivers report the server's interrupt (Postgres's 57014, MySQL's and MariaDB's 1317) as the server's error marked `Meaning::Interrupted`; the job makes it `DbError::Cancelled` only once it sent a cancel for that statement, so a timeout or another session's cancel stays the server's error. An Apply's is `Cancelled` when its gate was cancelled; SQLite's interrupt comes only from dbee and is always `Cancelled`. The drivers start no operation while a request is on its way (Postgres until the server has closed the request's connection, MySQL until `KILL QUERY` has its OK, SQLite's interrupt is a call that returns), so a cancel never reaches a later statement. Every operation on the browse connection, which the tabs share, first waits for its turn in the engine (`turns::InTurn`); a page load, a count or an Apply stopped before its turn leaves the queue and sends nothing, so its cancel reaches its own statement or none; a catalog refresh's 60 s limit counts from its turn. A result whose tab has gone is ignored. Dropping the session shuts the runtime down without waiting (safe in async code too); jobs still running are dropped with it.
4. **Journal.** Successful journaled commands with their params, in memory and replayable; the localhost control channel serves it (`engine.journal`). Secret params (`password`, `passphrase`, and keys ending in `Password` or `Passphrase`) and `trustHostKey` are left out at any depth. It keeps the newest 10,000 entries at most (it drops the oldest 5,000), and consecutive `query.setText` entries replace each other, as do consecutive `table.setFilters` entries with `apply: false` and the same keys (typing in the filter bar). Logs carry command ids, job labels, error codes and timings, and the host and port of the database or SSH server a connection reaches: never params, secrets, cell values or SQL text. The log file is 0600 in a 0700 folder where the OS has modes.
5. **Connections.** `connection.open`, `connection.test` and `connection.reconnect` are jobs: the SSH tunnel, the browse connection and (for open and reconnect) the catalog, whose load is bounded at 60 s. `connection.listDatabases` is one too, for the form's Database field: the tunnel, then a connection of its own that the driver opens through the server's default database (`Driver::list_connection`), whose `list_databases` read is bounded and cancelled as a catalog read is, then the connection and the tunnel close; a file type's driver opens none, and the command refuses a file type. They connect through the session's driver for the config's database type (`SessionOptions::drivers`), and a type without one is refused (`disabled`) before any job starts; the engine then holds each connection as `Arc<dyn Connection>` and builds and splits SQL in its dialect. Secrets come from the params, then the secret store, then nowhere; the store keeps them for saved connections only, each with the settings it was saved for, and those settings alone decide at the read, in the job, where it may go (not the connections file or a window's copy of it): the database password to the same database type, host, port and user, whichever database the settings name, the same tunnel (none on either side, or the same SSH host and port), TLS at least as strong (disable < prefer < require < verify-ca < verify-full, `require` with a CA file counting as `verify-ca`), the same CA file where either side checks with one, and no option that protects it less (MySQL's `allowPublicKey`) on where the saved settings had it off; the SSH password to the same SSH host, port and user; the key passphrase to those and the same key file. An older build's secret has no settings with it: the saved connection decides once, and it is stored again with them. Saving new settings forgets the stored secrets they no longer apply to, unless the save gives them again, and stores the others again for the new settings. The ones a connect used stay in memory, in crate-private fields, for reconnects. Unknown host keys, key passphrases, the SSH password and a missing database password come back as `needs…` errors. `createFile` lets a file driver make a missing database file (not for a read-only connection; an isolated run only in its folders). A browse operation that finds the connection gone marks the session `lost`, and commands that need the database are disabled ("connection lost — reconnect") until a reconnect replaces the connections, keeping the tabs. `connection.close` stops the running jobs (a cancel through the driver's cancel for those without a `Stop`, an Apply or a catalog load) and lets the connections go; a job whose connection or tab went away meanwhile is ignored (`{"ignored": true}`).
6. **Tables, edits and queries.** A connection has two sessions with the database, through the same tunnel when it has one (on SQLite, two connections to the file): the browse connection for the catalog, table pages, counts and Apply, and a query connection, opened on the first query run, for query tabs (one run at a time; Cancel goes through the driver's cancel). On MySQL and MariaDB the query connection keeps the server's `sql_mode` and tracks its current database, which a query tab's `USE` sets. The query session's transaction belongs to the connection (`Connected::transaction`): after each run, `query.commit` and `query.rollback`, the driver says whether one is open, as the server reported it (`Connection::transaction`: Postgres's ReadyForQuery status, MySQL's and MariaDB's `SERVER_STATUS_IN_TRANS` with a `COM_PING` after an error, SQLite's autocommit flag), never from the SQL, and the engine keeps which tab's run opened it. A lost or replaced query connection ends it. A table page is `SELECT … LIMIT 101 OFFSET …`, ordered by the chosen sort, then the row key; filters and values go in as quoted literals in the connection's dialect (with casts on Postgres). Staged edits stay in the tab until Apply writes them all in one transaction, or none; a failed Apply marks the row and keeps the edits. A query run keeps at most 10,000 rows per result and 256 MiB held in its results, each cell counted with its slot (`dbee_driver::result_cost`); a result whose columns do not fit in what is left fails alone, and the connection goes on. A new query connection with less TLS than the browse connection sends nothing, and the run fails. Results land in the tab that asked; a result whose tab or connection has gone is ignored.
7. **The UI is thin.** Panels read `Session::state()` and act only through commands. `Session::inspect()` is the JSON summary agents read (`document.inspect`).
8. **Programmatic calls never open dialogs.** Only menu-style invocation opens a dialog (`UiRequest::Dialog`, collected with `take_ui_requests`).

## Adding an engine

What a fourth engine touches, in the product and in the test kit. Nothing in the engine or the UI names an engine, so neither changes.

- **The driver crate**, `crates/<engine>/`: its `Driver` and `Connection` (and `Cancel`, which must start no statement while a request is on its way), registered in `xtask/src/layers.rs` as one `Class::Driver` line and in the workspace table above.
- **The registry line** in `crates/drivers/src/lib.rs`, with its dependency in `crates/drivers/Cargo.toml`.
- **The dialect:** its file `crates/sql/src/dialect/<engine>.rs` with its `Rules`, and in `crates/sql/src/dialect/mod.rs` the `mod` line, the `Dialect` variant, `Dialect::ALL` (which `all_holds_every_dialect_once` checks against an exhaustive match) and the `rules()` arm. A SQL shape no `Rules` field covers (another paging, string or literal form, batch separators) needs a new variant in shared code.
- **The database type:** its file `crates/config/src/kind/<engine>.rs` with its `KindInfo` (and options), and in `crates/config/src/connection.rs` the `DbKind` variant, `DbKind::ALL` (checked by `all_holds_every_kind_once`) and the `info()` arm.
- **For a file engine, the packaging:** `packaging/linux/dev.rosin.dbee.desktop` (`MimeType`), `packaging/linux/dev.rosin.dbee.metainfo.xml.in`, `packaging/windows/dbee.wxs` (`OpenWithProgids`), and the test that checks them in `apps/dbee/src/main.rs`.
- **The test kit:** its kind file `crates/testkit/src/kind/<engine>.rs` with its `KindInfo` (the test SQL), the `Kind` variant and its `info()` arm in `crates/testkit/src/lib.rs`; for a server engine, xtask's own `Kind` and its `SERVICES` row (`xtask/src/testdb.rs`), the server's block in `xtask/testdb/compose.yml`, its seed beside `xtask/testdb/seed.sql`, and its client in the tools image (`xtask/testdb/tools.Dockerfile`, `tools-init.sh`). The engine and UI suites then run on it through `for_each_engine`.
- **The docs:** its row here and in [`driver-parity.md`](driver-parity.md), and its limits in [`gaps.md`](gaps.md).

## Agent control

- Control channel: `dbee --control <port>`, JSON lines on `127.0.0.1`, after a token from a file only this user can read: [`control-protocol.md`](control-protocol.md). `cargo xtask run-isolated` runs the app with it on a throwaway home.
- CLI **(planned)**: [`cli.md`](cli.md).

## Platforms

Desktop only: macOS, Windows, Linux and FreeBSD, of which every row was built in the first test release (2026-10-29, from the M1 code) and only Linux x86_64 has been run, apart from Windows ARM64, which was installed and started ([`hardware-parity.md`](hardware-parity.md)). There is no web build and no wasm target, because a browser cannot open database connections. See [`releasing.md`](releasing.md) for the platform matrix and [`decisions.md`](decisions.md).

## Known gaps

M1's and M2's crates are all in place. The driver interface exists, and the engine and the UI reach databases only through it. PostgreSQL, MySQL, MariaDB and SQLite sit behind it and are registered in `drivers`, and the connection screen offers each of them. The MCP crate is empty, and the CLI prints its version. The ranked work list is [`gaps.md`](gaps.md).
