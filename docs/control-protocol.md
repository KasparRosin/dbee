# dbee control protocol

> **Last reviewed:** 2026-10-30 · **Last updated:** 2026-11-05 · **Change:** minor (a query tab's `startsIn` comes from the server's session tracking, which dbee stops trusting after a run that names `session_track`; a tab's `USE` is sent unless the connection is known to be there already)

The desktop app takes a control port, so agents and tests can drive the real window:

```sh
dbee --control 7979            # or DBEE_CONTROL_PORT=7979
cargo xtask run-isolated       # the same on a throwaway home (docs/agents.md §4)
```

The app listens on `127.0.0.1` only, before the window opens: a port in use stops the start, so an agent never drives another dbee by mistake. Any local process can connect, so it is meant for agents and tests. HTTP requests are refused (an `httpRefused` reply, then the connection closes, with nothing run), so web pages cannot use the channel through the browser. Send newline-delimited JSON; every request line gets one reply line, in order:

```json
{"id":1,"method":"engine.execute","params":{"command":"tab.newQuery","params":{"text":"select 1"}}}
{"id":1,"ok":true,"result":{"tab":1}}
```

Errors look like `{"id":…,"ok":false,"error":"…","code":"…","data":{…}}`. `code` is stable: an engine error's code (`disabled`, `badParams`, `unknownCommand`, `needsPassword`, `connectionLost`, `server`, `busy`, `timeout`, …) with its `data` (`{command, why}` for `disabled`; `{serverCode, detail, hint, position}` for `server`, `serverCode` being the server's own code, such as Postgres's SQLSTATE), or one of the channel's own: `invalidJson`, `badRequest` (not a request object, no `method`), `unknownMethod`, `badParams`, `notFound` (no such automation id), `lineTooLong`, `httpRefused`, `timeout`, `busy` (too many connections or too much queued input), `closed` (the app is closing), `screenshot`. A line that is not JSON gets an error reply and the server keeps serving; blank lines get none.

- A request line holds at most 64 MiB.
- `params` is an object (or left out). Every method takes `timeoutMs` (default 60,000, at most 600,000): how long its reply may wait. A reply that waits longer is a `timeout` error; a job it waited for goes on. A request still waiting to be handled when its reply timed out is not run.
- Requests are handled in the window's frames, so the window must be shown (not minimised) for replies to come.

## Methods

| Method | Params | Result |
|---|---|---|
| `engine.execute` | `{command, params?, wait? = true}` | Runs any command, engine or UI-only (`DbeeApp::run`). A command that starts a job is answered when the job's result is applied; with `wait: false` the reply is `{job}` at once. |
| `engine.commands` | `{search?}` | Every command: `{id, label, menu, shortcut, params, enabled, disabledReason}`. `search` keeps those whose id, label or a menu contains it, ignoring case. |
| `engine.journal` | | `[{command, params}]`: the commands run so far (replayable), without secret params. |
| `engine.wait` | | `{}` once no job runs. |
| `document.inspect` | | The session summary (`Session::inspect`): screen, `kinds` (the ids of the database types this build has a driver for, e.g. `["postgres"]`), connection (with its `kind`, and `server`: the product and its version, `PostgreSQL 14.12`), tabs, the active tab (a query tab's `database`, its own, made current with `USE` before a run unless the query connection is known to be there already, and `startsIn` `{database, known}`, where its next run starts: its own, else the database the query connection is in, as the server reports it after each statement (MySQL and MariaDB do in their OK packets, through session tracking; dbee sends no statement of its own to ask, and stops trusting the reports on a connection after a run that names `session_track`), `known: false` once a statement may have moved it without the server saying so, `database` then the last one known; a query tab's `error` with `serverCode` and `meaning`, `transactionAborted` when a statement failed earlier in the transaction, else null), selection, value view (`kind` is `json` for every JSON column, `jsonb` included, and `kindLabel` names the column's type), running jobs. Never a secret. When the app keeps its clipboard in memory (`DBEE_CLIPBOARD=memory`, which `cargo xtask run-isolated` sets), also `clipboard`, the first 4 KiB of the last copied text (cut on a character boundary), and `clipboardBytes`, its whole length; both `null` before any copy. In that mode every copy and cut stays in the app, a text field's (the query editor, a filter input, the connection form, the search boxes) as well as the grid's: at the end of each frame the app takes them all out of egui's output, so none reaches the system clipboard. Without the variable there are no such fields. |
| `ui.inspect` | | `{screen, dialog, window: [width, height], frame, editor, automation: [{id, rect: [x, y, width, height], visible?, value?, masked?, set?, enabled?}]}`. `frame` counts the frames drawn; `editor` is the open cell editor's `{row, column}`, also while its cell is out of view (a new one whose cell does not come into view within a second closes unchanged), or `null`; `dialog` names the open dialog (`fillFromUrl`, `hostKey`, `passphrase`, `password`, `sshPassword`, `confirm`, `deleteConnection`) or is `null`; `automation` lists the widgets of the last drawn frame, in window points. `rect` is the part of the widget in view; a widget scrolled out of view has `visible: false` and its whole rect. The cells of a grid's rows out of view come last, also with `visible: false` (at most 20,000 of them; the others are found by id all the same). `value` is what a widget shows (a field's text, a check box's state, a choice, a message); a password, passphrase or URL field has `masked: true` and `set` (whether it is filled in) instead, never its text. A disabled widget has `enabled: false`; this holds in the first frame of a dialog or a menu too, which egui draws all disabled. |
| `ui.click` | `{id}` or `{x, y}`, then `button?` (`left`, `right`, `middle`), `count?` (1–3), `modifiers?` (`{shift?, cmd?, alt?, ctrl?}`) | `{x, y}`, once the frame that got the click has run. `{id}` clicks the centre of that automation id; a widget scrolled out of view is scrolled into view first (`notFound` when that fails within 30 frames). |
| `ui.key` | `{key, shift?, cmd?, alt?, ctrl?}` | `{}`, once the key was handled. `key` is egui's name (`Enter`, `Escape`, `ArrowDown`, `A`, `F2`; `esc`, `down` and the like work too). `cmd` is Cmd on macOS and Ctrl elsewhere; with it, `C` and `X` arrive as copy and cut, as from the keyboard. Type text with `ui.text`. |
| `ui.text` | `{text}` | `{}`: the text typed into the focused field. |
| `ui.screenshot` | `{path?}` | A PNG of the window: written to `path` (relative to the app's working directory, folders created) as `{path, width, height}`, or `{base64, width, height}`. |
| `app.quit` | | `{}`; the window closes a frame later, after the reply is written. |

Planned: `ui.dialog.*` (open, fill in, confirm and cancel dialogs) and `app.open {path}`.

## Automation ids

Widgets agents drive have kebab-case ids, listed by `ui.inspect` and clicked with `ui.click {id}`. Each UI task lists its ids; today:

- the connection screen's lists: `conn-new`, `conn-filter`, `conn-store-warning`, `conn-saved-<id>` and `conn-recent-<n>` (cards, value: the name; `conn-saved-<id>-kind` and `conn-recent-<n>-kind` give the label of its database type, `MariaDB`; right-click for `conn-menu-connect`, `conn-menu-edit`, `conn-menu-duplicate`, `conn-menu-delete`);
- its card, `conn-card`, which holds the rest of the right side. Its title row: `conn-title` (cut to the room there is, with the whole title on hover) and `conn-fill-url` (Fill from URL: the URL's scheme picks the database type, so on the engine cards it skips them; a saved or recent connection's form takes its own type's URLs only, and has no Fill from URL when that type has none);
- the engine cards a new connection starts with: `conn-kind-<type>` (`conn-kind-postgres`, `conn-kind-mysql`, `conn-kind-mariadb`, `conn-kind-sqlite`; value `{label, upcoming}`, `upcoming` and disabled for a type this build has no driver for). A click opens the form for that type;
- its form: `conn-kind` (value: the type's id, on the title row, or on a row of its own under it when the card is too narrow for both) with `conn-change-engine` (back to the cards; the form keeps what was typed, and a port that still holds the old type's default takes the new one's; disabled while a test or connect runs, and not there for a connection opened from the saved list or Recent, whose type is fixed), `conn-name`, `conn-color` (and `conn-color-<colour>`); for a server `conn-host`, `conn-port`, `conn-user`, `conn-password`, `conn-password-show`, `conn-save-secrets`, `conn-no-keyring`, `conn-database`, `conn-ssl` (and `conn-ssl-<mode>`), `conn-ca`, `conn-ca-choose`, `conn-ca-clear`; for a file `conn-file` (value: the path, or null), `conn-file-choose` and `conn-file-new`; then `conn-readonly` and the type's options `conn-option-<id>` (MySQL's and MariaDB's `conn-option-allowPublicKey`);
- a server's SSH tunnel: `conn-ssh-on`, `conn-ssh-host`, `conn-ssh-port`, `conn-ssh-user`, `conn-ssh-auth` (and `conn-ssh-auth-key`, `-agent`, `-password`), `conn-ssh-key` (what the login will use), `conn-ssh-change`, `conn-ssh-auto`;
- its buttons and their message: `conn-save`, `conn-test`, `conn-connect`, then `conn-error` (something failed), `conn-result` (a test passed, a save) or `conn-note` (anything else, such as a note about a file picker);
- dialogs: `dialog-ok`, `dialog-cancel`, `dialog-text`, `dialog-url`, `dialog-error`, `dialog-fingerprint`, `dialog-secret`, `dialog-save`;
- the workspace's menu bar: `menu-File`, `menu-Edit`, `menu-View`, `menu-Query` (one per top menu the commands name) and, while a menu is open, `menu-<command id>` (`menu-tab.newQuery`) with the value `{label, shortcut, why?}`, `why` saying why a disabled entry cannot run now. An entry runs its command as a button does, with its shortcut's params;
- its schema tree: `tree-filter`, `tree-refresh`, `tree-system` (the system schemas' group; "System databases" on MySQL and MariaDB), `tree-schema-<schema>` (a click selects it and opens or closes it; MySQL's are its databases), `tree-table-<schema>.<table>` (value: its kind; a click selects it, a double-click opens it), `tree-expand-<schema>.<table>` (shows its columns) and `tree-column-<schema>.<table>.<column>` (value `{type, key}`, `key` being `primary`, `foreign` or null). Schema and table rows out of view are listed with `visible: false`, and a click scrolls them into view first. The catalog's default schema (Postgres `public`, the database a MySQL connection names, SQLite `main`) is listed first and starts open. A query tab the window opens (Ctrl+T, `tab-new`, the File menu) gets the selected schema, or the selected table's, as `tab.newQuery`'s `schema`; a selection the catalog no longer holds after a refresh or a reconnect is forgotten. `tree-refresh`'s hover names the engine's word ("Refresh the databases" on MySQL and MariaDB);
- its tabs: `tab-<id>` (value: the title as shown, `orders [2]` when 2 filters are applied; a middle click closes it), `tab-close-<id>`, `tab-dirty-<id>` (the dot of a tab whose query text or staged edits closing would lose), and `tab-new`;
- its status bar: `status-connection` (value: the connection's name, with `read-only` when the session is), `status-server`, `status-job` (value: what runs in the active tab, or a reconnect) with `status-cancel` (for a page load, a count, a query run, and an Apply until it commits: a cancelled Apply writes nothing and keeps its edits, while one that is committing runs to its end and the click says `The changes are being committed.`), `status-lost` with `status-reconnect` while the connection is lost, and at its right end `value-toggle` (value: whether the value panel shows; a click hides or shows it, as `ui.toggleValuePanel` and the View menu do);
- the value panel on the right, which follows the grid's selected cell (its focus cell), staged values included: `value-panel` (value `{column, type, label, null, bytes, truncated, note}`: `label` is a JSON column's type as the engine names it (`jsonb`, `json`), `text containing JSON`, `JSON string containing JSON` or null, `bytes` the whole value's length, `note` what a value cut to 10 MiB says, e.g. `Showing the first 10.0 MiB of 19.1 MiB.`; the value is null when no cell is selected) and `value-text` (value `{text, cut, selection, highlighted, rows, firstRow}`: the text's first 4 KiB and whether there is more, the selection as `[start, end]` byte offsets or null, whether the JSON colours show, the number of wrapped rows and the first in view). The text is read-only: a click places the caret and gives the panel the keyboard, a shift-click or a drag selects, a double-click selects a word; with text selected Ctrl+C (and Ctrl+Shift+C, as in a text field) copies it instead of the grid's cells, and while the panel has the keyboard Ctrl+A selects all of it. The text wraps at the panel's width by columns (a tab four, an emoji or a CJK character two); another view of the same text (a staged edit elsewhere, an undo) keeps its scroll, selection and colours. A click elsewhere ends the selection. Its width (dragged at its left edge) and whether it shows last for the session;
- the quick search (Ctrl+P): `qs-input` and `qs-item-<n>` (value `schema.table`, best first, `n` from 0). ArrowDown and ArrowUp move, Enter opens, Escape closes;
- a table tab: `table-note` (value: why its rows cannot be edited, shown above the grid when they cannot, on one line: cut short when long, whole on hover) and `table-error` (value: the server's message of the last Apply that failed, whose changes stay staged with the failed row marked; else the message of the last page load that failed, an inline card over the rows from before);
- its filter bar: `filter-<n>-column` (value: the column; while open its choices `filter-<n>-column-<column>`), `filter-<n>-op` (value: the operator's id; its choices `filter-<n>-op-<id>`, e.g. `filter-0-op-gt`; an operator that does on the engine what its words do not say, such as MySQL's collation, says so on hover), `filter-<n>-value`, `filter-<n>-remove`, `filter-add`, `filter-raw-toggle` (value: whether the raw `WHERE` field shows), `filter-raw` and `filter-apply`. Enter in a value field applies too. `is null` and `is not null` have no value field. While changes are staged, typing goes on but `filter-apply` is disabled;
- its grid: `grid-header-<col>` (value `{name, type, key, sort}`, `key` being `primary`, `foreign` or null, `sort` `asc`, `desc` or null; a click sorts), `grid-cell-<row>-<col>` (value `{text, null, state?, deleted?}`: the text as shown, cut to 200 characters, `NULL` with `null: true` for NULL, `state` being `staged`, `new`, `deleted` or `failed`, and `deleted: true` on a row to delete, also when it is the failed one; shift-click extends the selection, right-click opens the menu), `fk-link-<row>-<col>` (the foreign key link in the selected row) and, while the right-click menu is open, `grid-menu-null`, `grid-menu-copy`, `grid-menu-copy-header`, `grid-menu-copy-csv`, `grid-menu-copy-json`, `grid-menu-copy-markdown` and `grid-menu-delete` (value `{label, shortcut, why?}`, `why` saying why a disabled entry cannot run now: on a read-only table, `views are read-only`, say). A click, right-click or drag on a cell takes the keyboard from a text field (the query editor, a filter input), so Ctrl+A, Ctrl+C and Ctrl+Shift+C then act on the grid; while a text field has the keyboard they are its own. Every copy from the grid (Ctrl+C values only, Ctrl+Shift+C with the header, the menu's formats, `clipboard.copy`, which returns `{rows, columns, bytes}`) shows `Copied n rows` in `notice`. A copy's text is at most 8 MiB, everything counted (quotes, escapes, `NULL`, column names); one that would be longer copies nothing and says so there, with how many of the selected rows fit. Rows and columns are 0-based, as in `selection.set`; a cell of a row or column out of view is scrolled into view by `ui.click`. A double-click on a cell (`ui.click` with `count: 2`), or Enter with the grid's selection and no field focused, opens its editor `cell-editor` (value `{text, multiline}`, the text cut to 200 characters; for a boolean `{choice}`, `true`, `false` or `null`, with the choices `cell-editor-true`, `cell-editor-false` and `cell-editor-null`). In it Enter commits (a newline in `text`, `json`, `jsonb` and `xml`, where Ctrl+Enter commits), Tab commits and selects the next cell (Shift+Tab the one before), Escape cancels, and a click elsewhere, or scrolling its cell out of view, commits; an unchanged value stages nothing. A cell that cannot be edited opens no editor and says why in `notice`, as does a value over 32 KiB, or a paste that would make it longer. When the staged changes change under an open editor (an `engine.execute` of `row.delete`, say), it closes without committing and `notice` says the edit was discarded;
- its paging bar: `page-first`, `page-prev`, `page-number` (value `Page 3`, or `Page 3 of 10` once counted), `page-next`, `page-last`, `page-count` (value: `~100,000 rows` while only the estimate is known, `100,000 rows` once counted, else `Count rows`; a click counts. Short of room it shows as a square icon button with that text on hover, and its value stays the text), `table-refresh`, `page-cut` (value: the note on a page the size limit cut short; not drawn without room for it), `row-add` ("+ Row": stages a new row and selects its first cell; disabled, with the reason on hover, where rows cannot be edited), and with staged changes `edits-count` (value `2 changes`; not drawn while the bar is short of room, when Apply's hover says it), `edit-reset` and `edit-apply` (Ctrl+S too, which commits an open editor first). No control of the bar is drawn over another: short of room the count becomes the icon first, then `edits-count` goes, and in a bar narrower than both groups need, the right group (from `row-add` on) is cut at the bar's edge;
- a query tab: its SQL editor `query-editor` (value `{cursor, focused, lines, length, highlighted}`: the cursor as a byte offset into the text, whether the editor has the keyboard, the number of lines, the text's length in bytes and whether some token is coloured; a new or newly active query tab's editor takes the keyboard, so `ui.text` types into it). Ctrl+Enter runs every statement and Ctrl+Shift+Enter the one under the cursor (neither puts a newline in), Tab inserts four spaces, Shift+Tab does nothing, Escape takes the keyboard away. `query-split` (value: the editor's share of the height) is dragged to move the line between the editor and the results; it lasts for the window's run. On an engine with `USE` (MySQL, MariaDB) the toolbar starts with `query-database` (value: the database the tab's next run starts in, the engine's `startsIn`, or null for none or not known; disabled while the tab runs or Run cannot, and its list closes then): a click lists the catalog's databases, the server's own left out, as `query-database-<name>`, and choosing one runs `query.setDatabase`, which sets the tab's own. After a run that got past the tab's `USE`, the tab's database is the one the query connection is then in, so a `USE` in its text sticks to it. The toolbar has `query-run` and `query-run-current` (enabled as `query.run` is: connected and the connection not lost, else disabled with the reason on hover; what the run refuses, such as a text with no statement or a run already going, shows in `notice`) and `query-cancel` (enabled while the tab's run goes), with several results the selector `result-<n>` (`n` from 1, while `query.showResult` takes the 0-based index; value `{shown, rows, rowsAffected}`; with more results than fit, only those around the shown one are drawn), and `query-rows` (value: `3 rows`, or the cap notice `First 10,000 of 25,000 rows`). A statement without rows shows `query-affected` (value: `1 row affected`) instead of a grid. The last run's error is the card `query-error` (value `{code, heading, message, detail, hint, note, position, statement, line, column, jump}`; `note` is the card's line under an error whose `meaning` is `transactionAborted` (Postgres's SQLSTATE 25P02), saying that a ROLLBACK ends the failed transaction the query connection is in, else null; `code` is `cancelled` for a cancelled run, which shows in neutral colours): a click puts the cursor at the error's position, with the keyboard, when `jump` is true. It sits above the results, and the results of the statements before the failing one stay. With nothing run yet, `query-hint` says how to run. The result grid has the grid ids listed above for a table tab, read-only: no sorting, editing or links, and its menu lists no `grid-menu-null` or `grid-menu-delete`;
- `notice` (the notice shown at the bottom right; value: its text). A click on something that cannot run now (a header's sort while changes are staged, say) shows why there: the reason alone, as a sentence (`Apply or reset your changes first.`), as for a command that is busy or got bad params. The control channel's error keeps the command (`` `table.sort` cannot run now: apply or reset your changes first ``).

The file pickers (`conn-ssh-change`, `conn-ca-choose`, `conn-file-choose`, `conn-file-new`) open the desktop's picker, which agents cannot drive: save a connection with the path instead (`connection.save`) and click its card. `connection.test` and `connection.open` make a missing database file with `createFile: true`, as New file… does: anywhere the user can write, except in an isolated run, which allows only its folders (`DBEE_ALLOW_DIRS`). It is not for a read-only connection (`badParams`). An existing file opens as it is, so the form sends it with every test and connect after New file… until a connect succeeds, and the journal's `connection.open` carries it.

## Rules

- Programmatic calls never open dialogs. `engine.execute` with empty params runs with defaults or returns an error; a command that needs an answer (a password, a host key) returns a `needs…` error with the details in `data`, and is run again with the answer in its params.
- Params are hostile input: wrong types, missing keys and deep nesting are errors, never panics ([never crash](standards/never-crash.md)).
- Passwords are never echoed in replies or the journal. The log names methods and command ids only, never params, SQL or values.
