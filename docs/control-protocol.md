The desktop app takes a control port, so agents and tests can drive the real window:

```sh
dbee --control 7979            # or DBEE_CONTROL_PORT=7979
cargo xtask run-isolated       # the same on a throwaway home (docs/agents.md §4)
```

The app listens on `127.0.0.1` only, before the window opens: a port in use stops the start, so an agent never drives another dbee by mistake. A client proves itself with a token only this user can read, and the app proves itself back (see [Connecting](#connecting)). It is meant for agents and tests. HTTP requests are refused (an `httpRefused` reply, then the connection closes, with nothing run), so web pages cannot use the channel through the browser. After the token, send newline-delimited JSON; every request line gets one reply line, in order:

```json
{"id":1,"method":"engine.execute","params":{"command":"tab.newQuery","params":{"text":"select 1"}}}
{"id":1,"ok":true,"result":{"tab":1}}
```

Errors look like `{"id":…,"ok":false,"error":"…","code":"…","data":{…}}`. `code` is stable: an engine error's code (`disabled`, `badParams`, `unknownCommand`, `needsPassword`, `connectionLost`, `server`, `busy`, `timeout`, …) with its `data` (`{command, why}` for `disabled`; `{serverCode, detail, hint, position}` for `server`, `serverCode` being the server's own code, such as Postgres's SQLSTATE), or one of the channel's own: `invalidJson`, `badRequest` (not a request object, no `method`), `unknownMethod`, `badParams`, `notFound` (no such automation id), `lineTooLong`, `httpRefused`, `unauthorized`, `timeout`, `busy` (too many connections or too much queued input), `closed` (the app is closing), `screenshot`. A line that is not JSON gets an error reply and the server keeps serving; blank lines get none.

- A request line holds at most 64 MiB.
- `params` is an object (or left out). Every method takes `timeoutMs` (default 60,000, at most 600,000): how long its reply may wait. A reply that waits longer is a `timeout` error; a job it waited for goes on. A request still waiting to be handled when its reply timed out is not run.
- Requests are handled in the window's frames, so the window must be shown (not minimised) for replies to come.

## Connecting

Once it holds the port, each start of the app writes a token file with two random lines, new each start. Only this user can read it (the file is `0600` and its folder `0700` where the system has file modes), and the app removes it when it ends. On Windows dbee sets no rights on the file, which takes its folder's: under the user's profile that keeps other accounts out, and elsewhere (a repository outside the profile, say) it may not. This is not measured.

| Started by | The token file |
|---|---|
| `cargo xtask run-isolated --port <port>` | `target/isolated/<port>/control-token` |
| `dbee --control <port>` | `control-<port>.token` in the settings folder (on Linux, `~/.config/dbee/`; for the other systems see [README.md](../README.md#L61)), or wherever `DBEE_CONTROL_TOKEN_FILE` says |

The settings folder is used also with `DBEE_NO_PREFS`: the token has to live somewhere, so that run writes the token file there and leaves it (the folder stays) after it ends, though it keeps no connections file, no settings file and no log file. A file named by `DBEE_CONTROL_TOKEN_FILE` wants a folder of its own: that folder becomes `0700`, so a folder others can write in is no place for it, and a start that cannot make the file stops and says so. Give each run its own file: two starts that name one file replace each other's lines, and only the later one can be reached by a new client.

To connect:

1. Read the file.
2. Connect to `127.0.0.1:<port>` and send the file's first line as your first line. Use `127.0.0.1` as written, not `localhost`: `localhost` can resolve to `::1`, where dbee holds no port, so another process could listen there and hear the token.
3. Read the reply, `{"id":null,"ok":true,"result":{"proof":"…"}}`, and compare `proof` with the file's second line. If they differ, or the reply is anything else, you are not talking to the dbee that wrote the file: close the connection and send nothing more, above all no password.

```python
import json, socket

token, proof = open("target/isolated/7983/control-token").read().split()
s = socket.create_connection(("127.0.0.1", 7983))
r = s.makefile("rb")
s.sendall((token + "\n").encode())
assert json.loads(r.readline())["result"]["proof"] == proof
s.sendall(b'{"id":1,"method":"ui.inspect"}\n')
print(r.readline())
```

For one request from a shell on Linux (`nc -q` is not on every system; the Python client above is; this sends the request before it has seen the proof, so keep passwords out of it, and read the proof in the first reply line):

```sh
{ head -n 1 target/isolated/7983/control-token; echo '{"id":1,"method":"ui.inspect"}'; } | nc -q 5 127.0.0.1 7983
```

- A first line that is not the token gets one `unauthorized` reply, and the connection closes with nothing run. So does one longer than 4 KiB, or one that takes longer than 10 seconds to arrive. An `unauthorized` right after a start means the file was read before the new start wrote it: read it again.
- The token works for every connection of that start, and for none after it. A file left by a run that was killed does no harm: a client that reads it gets no proof it can match, and the next start replaces it.
- The file is written only after the port is taken. A start that finds the port in use stops and leaves the running app's file alone.
- A start that cannot write the file stops too, and says why.

## Methods

| Method | Params | Result |
|---|---|---|
| `engine.execute` | `{command, params?, wait? = true}` | Runs any command, engine or UI-only (`DbeeApp::run`). A command that starts a job is answered when the job's result is applied; with `wait: false` the reply is `{job}` at once. |
| `engine.commands` | `{search?}` | Every command: `{id, label, menu, shortcut, params, enabled, disabledReason}`. `search` keeps those whose id, label or a menu contains it, ignoring case. |
| `engine.journal` | | `[{command, params}]`: the commands run so far (replayable), without secret params and without `trustHostKey`, so a replay asks about an unknown host key again. |
| `engine.wait` | | `{}` once no job runs. |
| `document.inspect` | | The session summary (`Session::inspect`): screen, `kinds` (the ids of the database types this build has a driver for: `["postgres", "mysql", "mariadb", "sqlite"]`), connection (with its `kind`, `server`: the product and its version, `PostgreSQL 14.12`, and `saved`: whether the saved list holds it), tabs, the active tab (a query tab's `database`, its own, made current with `USE` before a run unless the query connection is known to be there already, and `startsIn` `{database, known}`, where its next run starts: its own, else the database the query connection is in, as the server reports it after each statement (MySQL and MariaDB do in their OK packets, through session tracking; dbee sends no statement of its own to ask, and stops trusting the reports on a connection after a run that names `session_track`), `known: false` once a statement may have moved it without the server saying so (a cancelled statement, or a report that does not decode, counts), `database` then the last one known; a query tab's `error` with `serverCode` and `meaning`: `transactionAborted` when a statement failed earlier in the transaction, `interrupted` when the server stopped the statement and dbee had sent no cancel for it (a timeout, another session's cancel), else null; a table tab's `saved`, `[[row, column], …]`: the cells of the page shown that the last successful Apply wrote, found on the page it loaded again by their rows' keys, so a row the write moved shows its mark where it went, and a row it moved off the page, a deleted row and a new row whose key the database chose have none; another Apply, any other page load, a reconnect, and a reset, undo or redo empty it, and staging an edit on a cell takes that cell out), selection (`{anchor, focus, whole}`: `whole` is true for rows selected by their numbers, `selection.rows`, which span every column; `selection.set` and `selection.all` select cells, `whole: false`), value view (`kind` is `json` for every JSON column, `jsonb` included, and `kindLabel` names the column's type; `row` is null for a cell, and for whole rows the number of the focus row as the grid shows it, the view then being that row's JSON object, see `value-panel`), running jobs. Never a secret. When the app keeps its clipboard in memory (`DBEE_CLIPBOARD=memory`, which `cargo xtask run-isolated` sets), also `clipboard`, the first 4 KiB of the last copied text (cut on a character boundary), and `clipboardBytes`, its whole length; both `null` before any copy. In that mode every copy and cut stays in the app, a text field's (the query editor, a filter input, the connection form, the search boxes) as well as the grid's: at the end of each frame the app takes them all out of egui's output, so none reaches the system clipboard. Without the variable there are no such fields. |
| `ui.inspect` | | `{screen, dialog, window: [width, height], frame, editor, theme: {choice, mode}, automation: [{id, rect: [x, y, width, height], visible?, value?, masked?, set?, enabled?}]}`. `frame` counts the frames drawn; `theme` is the colour choice (`system`, `light`, `dark`) and the mode drawn (`light` or `dark`); `ui.themeSystem`, `ui.themeLight` and `ui.themeDark` (View > Theme, no params) choose and keep it, answering `{choice, mode}`, and `system` follows what the desktop said at startup; a choice that cannot be kept still applies, with a notice. `editor` is the open cell editor's `{row, column}`, also while its cell is out of view (a new one whose cell does not come into view within a second closes unchanged), or `null`; `dialog` names the open dialog (`fillFromUrl`, `hostKey`, `passphrase`, `password`, `sshPassword`, `confirm`, `transactionEnd`, `deleteConnection`) or is `null`; `automation` lists the widgets of the last drawn frame, in window points. `rect` is the part of the widget in view; a widget scrolled out of view has `visible: false` and its whole rect. The cells of a grid's rows out of view come last, also with `visible: false` (at most 20,000 of them; the others are found by id all the same). `value` is what a widget shows (a field's text, a check box's state, a choice, a message); a password, passphrase or URL field has `masked: true` and `set` (whether it is filled in) instead, never its text. A disabled widget has `enabled: false`; this holds in the first frame of a dialog or a menu too, which egui draws all disabled. |
| `ui.click` | `{id}` or `{x, y}`, then `button?` (`left`, `right`, `middle`), `count?` (1–3), `modifiers?` (`{shift?, cmd?, alt?, ctrl?}`) | `{x, y}`, once the frame that got the click has run. `{id}` clicks the centre of that automation id; a widget scrolled out of view is scrolled into view first (`notFound` when that fails within 30 frames). |
| `ui.key` | `{key, shift?, cmd?, alt?, ctrl?}` | `{}`, once the key was handled. `key` is egui's name (`Enter`, `Escape`, `ArrowDown`, `A`, `F2`; `esc`, `down` and the like work too). `cmd` is Cmd on macOS and Ctrl elsewhere; with it, `C` and `X` arrive as copy and cut, as from the keyboard. Type text with `ui.text`. |
| `ui.text` | `{text}` | `{}`: the text typed into the focused field. |
| `ui.screenshot` | `{path?}` | A PNG of the window: saved as `{path, width, height}`, or sent back as `{base64, width, height}` without `path`. `path` is a file name such as `shot.png`, in the run's one screenshot folder, and the reply's `path` is the whole path of the file. An absolute path, a folder in the name, `..` and the like are `badParams`. The same name again replaces a file, but a link or a folder of that name is a `screenshot` error and stays as it is. The file is `0600`, as a picture can show data. The folder is `target/look` in `cargo xtask run-isolated`; otherwise `DBEE_SCREENSHOT_DIR`, else `screenshots` in the settings folder, made when needed. In an isolated run a folder outside the run's allowed folders (`DBEE_ALLOW_DIRS`) is a `screenshot` error, and nothing is made. |
| `app.quit` | | `{}`; the window closes a frame later, after the reply is written. It asks nothing, unlike closing the window by hand ([Closing the window](#closing-the-window)). |

Planned: `ui.dialog.*` (open, fill in, confirm and cancel dialogs) and `app.open {path}`.

The file pickers (`conn-ssh-change`, `conn-ca-choose`, `conn-file-choose`, `conn-file-new`) open the desktop's picker, which agents cannot drive: save a connection with the path instead (`connection.save`) and click its card. `connection.test` and `connection.open` make a missing database file with `createFile: true`, as New file… does: anywhere the user can write, except in an isolated run, which allows only its folders (`DBEE_ALLOW_DIRS`). It is not for a read-only connection (`badParams`). An existing file opens as it is, so the form sends it with every test and connect after New file… until a connect succeeds, and the journal's `connection.open` carries it.

A command's `config` (`connection.save`, `connection.test`, `connection.open`, `connection.listDatabases`, `connection.sshKey`) with a key dbee does not know is refused with `badParams` naming it (`ssh.<key>` for one of the tunnel's, `ssh.auth.<key>` for one of its login's), so a misspelt `"hots"` is not saved quietly. `connection.test` returns `{server, via, warnings}`: `via` says how it got there, `direct` or the tunnel's login, and is `null` for a type that takes no tunnel, such as SQLite.

`connection.listDatabases {config, password?, sshPassword?, sshPassphrase?, trustHostKey?}` returns `{databases: [name]}`, the server's databases for the form's Database field: `config` is the form's (saved or not), and the password, the secret store, the SSH prompts and an isolated run's allowed targets work as for `connection.test`. It is a job that opens a connection of its own (through the tunnel when there is one), reads the list and closes it, so it leaves the session as it is, connected or not. The list is read through the server's default database, whatever the config names: Postgres connects without a database (so to the one named like the user) and, when that one does not exist (`3D000`), once more to `postgres`, and lists the databases that take connections, templates left out; MySQL and MariaDB connect without a database and list their own (`mysql`, `information_schema`, `performance_schema`, `sys`) last. The read is bounded as a catalog read is (60 s, then cancelled), after the connect's own 15 s. A file type (SQLite) is refused (`badParams`): its file is one database. It is not journaled, as its params can carry a password, the same as `connection.test` and `connection.parseUrl`.

`quickSearch.find {query, limit?}` (default 20) returns the hits, best first, by the same fuzzy score: the open connection's tables (none while not connected or while the connection is lost) and the saved connections but the open one (left out by its id), mixed by score, then the shorter name, a table first on a tie; with nothing typed, the tables in their own order, then the connections in the saved list's. A word starts at the beginning or after `.`, `_`, a space or `-`, and a match there scores more. Every hit names its kind in `hit`. A table is `{hit: "table", schema, table, kind}`, `kind` being the relation's (`table`, `partitionedTable`, `view`, `materializedView`, `foreignTable`). A saved connection is `{hit: "connection", id, name, dbKind, kindLabel, color}`: `name` is its display name, which the query is scored on (a file connection without a name by its file name), `dbKind` its database type's id and `kindLabel` that type's label, `color` its colour (`none`, `red`, …). Recent connections are not searched. It needs no connection: without one it finds saved connections only.

`connection.openFile {path, password?}` opens a database file as a file manager hands one over, never making it. When a saved connection's file is that file (both resolved: links followed, `.` and `..` gone), that saved connection opens, with its name, colour and read-only setting (`saved: true`). Else its type is the first of `kinds` whose file extensions hold the path's, in any letter case, and a path of no such type is refused (`badParams`) with a sentence naming the extensions dbee opens and saying that a file with another name opens through New connection; that connection is not saved (`saved: false`, the file's name as its name) and goes to Recent as every open does, and `connection.saveOpen` saves it as `connection.save` would, with the secrets it was opened with when its `saveSecrets` is on. `savePassword`, `sshPassword`, `sshPassphrase` and `trustHostKey`, which `connection.open` takes, are refused (`badParams`). A file dropped on the window, or the first argument of the command line that is no flag, runs it; its refusal shows in `notice`. A file dropped while a connection is open closes that one first, through `connection.close` and its question about an open transaction, unsaved query text and staged changes, as a switch in the quick search does (Cancel keeps everything), unless the file would be refused anyway: then the refusal shows and nothing closes. A drop while a dialog shows or a connect runs is let go. An isolated run allows only its folders here too.

Each connection that `connection` and `connections` show, and `connection.open` returns, also holds `tls`: what protects the link to the server, `off`, `unchecked` (TLS whose certificate dbee did not check), `certificateChecked` (checked against the CA file, not the server's name) or `checked` (the certificate and the name), and `null` for a file. A `prefer` connection that ended without TLS has a warning saying so in `warnings`, also as a notice on a reconnect, when its direct link reached an address on the network; to a loopback address, over a Unix socket or through an SSH tunnel it has none. On a link without TLS, direct or through a tunnel, dbee never sends the password in clear text: a server that asks for it so fails the login with `clearPassword`, which is dbee's own refusal and asks for no password, on Postgres as on MySQL and MariaDB. Over a Unix socket, which never leaves the machine, Postgres gets it when it asks. A run whose query connection got less TLS than the connection it belongs to sends nothing and fails. A result whose columns do not fit in what is left of a run's memory fails with `tooLarge`, and the connection goes on.

Each connection the session opens has an id, a whole number: a new one for each open (ids count from 1 in each session and are never reused), kept by `connection.reconnect`. It is not the saved connection's `id`. `document.inspect` lists the open connections in `connections`, each as `connection` shows it, and `connection` is the active tab's connection (with no tab active, the one opened last). Each of them holds the id as `connection`; `id` is still the saved connection's. Every tab in `document.inspect`'s `tabs` and in `tab.list` names its connection's id in `connection`: `null` for a query tab opened while no connection was open, which joins the next connection that opens. `connection.close`, `connection.reconnect`, `connection.saveOpen`, `schema.refresh`, `schema.inspect`, `quickSearch.find`, `table.open` and `tab.newQuery` take an optional `connection`, the id; left out, it is the active tab's connection. An id that is not open is refused with `badParams` (`no connection 3 is open`). The other tab commands act on their tab's connection. The id is also in the results that concern a connection: in the `connection` of `connection.open`, `connection.openFile` and `connection.reconnect`, and as `connection` in those of `connection.close`, `connection.saveOpen` and `schema.refresh`. Closing a connection closes its tabs. One connection can be open at a time: `connection.open` and `connection.openFile` are disabled while one is (`already connected; disconnect first`). The journal keeps `connection` only where the caller gave it; replayed in a new session that opens the same connections in the same order, the ids are the same.

`connection.cancel {}` stops the connection attempt that runs: that of `connection.open`, `connection.openFile`, `connection.reconnect` or `connection.test` (each that runs: a test can run beside another attempt). It returns `{stopped: true}`, and `{stopped: false, stopping: true}` when asked again before the attempt has ended; with none running it does nothing and returns `{stopped: false, note: "no connection attempt is running"}`, which is no error. The attempt then ends at once wherever it is (the TCP connect, the SSH tunnel's handshake or login, the database's login, the catalog's load, a secret store that is slow to answer), instead of when the connect limit passes (15 s a step): the socket it was using is closed, then the tunnel, and nothing it opened is kept. Each of the four commands then fails with code `cancelled`, the message `the connection attempt was cancelled` and no `data`; so does an attempt whose work had ended when the cancel came but whose result was not applied yet, and the connection it made is closed. Nothing else changes: a cancelled open or test leaves the screen and Recent as they were, and a cancelled reconnect leaves the connection as it was, lost or not, with its tabs. `connection.listDatabases` is no attempt it stops. Not journaled.

`query.cancel {}` returns `{tab, sent}`: `sent: true` when it stopped the active tab's run, whose job then sends the cancel request itself, again after 1 s and then every 2 s while the statement has not ended (a request that reaches the server before the statement does is lost), and never to a later statement; `sent: false` when the tab runs nothing. Called again while the run stops, it sends nothing itself: `{tab, sent: false, stopping: true}`. `table.cancel {}` does the same for the active table tab's page load and count (`{sent}`, `{sent: false, stopping: true}`); one still waiting for its turn on the browse connection, which the tabs share, leaves the queue and sends nothing, as a request would stop the tab ahead of it; so does the tab's own Apply, and while the tab's own Apply runs, `{sent: true, apply: true}`.

Each connection that `connection` and `connections` show also holds `transaction`, its query session's: `null` when none is open (also while no query connection is open, and once it was lost), else `{state, tab}`. `state` is `open`; `failed` on Postgres, when a statement failed inside it and the server refuses every statement until a ROLLBACK; or `unknown`, when dbee cannot tell (a run whose result was not applied, or a Postgres server whose messages dbee could not follow). `tab` is the query tab whose run found the session idle and left it in a transaction; a run of another tab keeps it, and it is `null` once that tab has closed (with `force`, which ends nothing; see `tab.close` below) or while the state is unknown. All of a connection's query tabs share its query session, so the state is the connection's, whichever tab is active. After each run, commit and rollback, dbee asks the driver, which says what the server reported and never reads the SQL to guess: Postgres in each ReadyForQuery message, MySQL and MariaDB in the status of each OK and EOF packet (after an error, whose packet has none, in the answer to a `COM_PING`), SQLite in its autocommit flag; no statement is sent to ask. So a `BEGIN` in a script, MySQL's `SET autocommit = 0` followed by a write, and a statement that commits on its own (MySQL's and MariaDB's `CREATE`, `ALTER`, `DROP` and the like) read as they are. Table tabs, their counts and Apply run on the browse session and leave it as it was. `connection.reconnect` and a lost query connection end it, as the server rolls it back: `null`.

`query.commit {tab?}` and `query.rollback {tab?}` send `COMMIT` or `ROLLBACK` on the query session from any of the connection's query tabs (`tab`, default the active one; a table tab or a tab that is not open is `badParams`), as a job that counts as the connection's run (`busy` while a run, a commit or a rollback goes; a run asked meanwhile says `a COMMIT is running`). They return `{tab, sent: true, transaction}`, the state after it, `null` once it has ended. With no transaction open they send nothing and return at once `{tab, sent: false, transaction: null, note: "no transaction is open"}`, which is no error. After a Postgres statement failed in a transaction (`25P02` from then on), `query.rollback` ends it; so does `query.commit`, as the server rolls a failed transaction back, and it adds `note: "the transaction had failed, so the server rolled it back: nothing was committed"`. When the query connection is found lost, `query.commit` fails with `connectionLost` (nothing was committed), and `query.rollback` returns `sent: false` with a `note` saying the server rolled the transaction back. Neither is journaled, and neither is in a menu yet.

`tab.close {tab?, force?, end?}` and `connection.close {connection?, force?, end?}` ask before they lose something: a `needs…` error, and nothing closes. `force: true` skips every question. Closing the query tab whose run opened the transaction (its `tab`) while that is `open` or `failed`, or closing a connection whose query session has one in any state, returns `needsTransactionEnd` with `data` `{state, about, name, lost, running}`: `state` is the transaction's; `about` is `tab` or `connection`, and `name` the tab's title or the connection's display name; `lost` is what the close loses besides, as the `needsConfirm` it comes before words it after its question, or `null`; `running` is the connection's query runs still going, `{title, count}` with the first one's tab title, or `null`. That `needsConfirm` (`what: "queryText"` or `"stagedEdits"`, asked when there is no transaction) has the message `<question> <lost>`, its question being `Close <tab>?` or `Disconnect from <connection>?`: `Close Query 1? Its query text will be lost.`, `Disconnect from Shop? The text of 1 query tab and the staged changes of 2 table tabs will be lost.` Closing any other tab asks nothing about the transaction; once its tab has closed with `force`, only closing the connection asks.

Run again with `end: "commit"` or `"rollback"`, the close is a job that counts as the connection's run (a run asked meanwhile says `a COMMIT or ROLLBACK is running before a close`): it sends `COMMIT` or `ROLLBACK` on the query session as `query.commit` and `query.rollback` do, then closes without asking, and returns the close's result plus `ended` (`"commit"` or `"rollback"`) and, when there is one, `note`: `no transaction is open` when it had ended meanwhile, which is no error; the failed Postgres transaction's note; the rolled-back note of a query connection found lost. When the end fails, the server refusing the `COMMIT` (a deferred constraint) or the query connection lost under a commit, the job fails with that error, nothing closes, and `transaction` is what the server reports after. While a query run goes on the connection, it is inside the transaction and only a rollback ends it: `end: "commit"` is `badParams` (`a statement is still running in the transaction; it can only be rolled back`), and `end: "rollback"` stops the run first (it ends `cancelled`), then rolls back and closes. While a commit or rollback runs, `end` is `busy`.

A run, a page load, a count or an Apply ends `cancelled` only when dbee stopped it: before its statement started, or with a cancel request dbee sent for that statement. A statement the server stopped by itself fails as any server error does, with code `server`, the server's code in `serverCode` and its words: Postgres's `57014` (a `statement_timeout`, or another session's `pg_cancel_backend`) and MySQL's and MariaDB's `1317` (another session's `KILL QUERY`). A query tab's `error` then has `meaning: "interrupted"`. A statement that ended before the cancel reached it keeps its result, also when Cancel came after its end, and the next run is not affected. When a server's timeout lands while dbee's own request is on its way, Postgres gives both the same code, and the run reads as cancelled: the user asked for the stop. SQLite has no timeout of its own: its interrupt comes only from dbee and is always `cancelled`.

### Closing the window

Closing the window by hand (its close button, Alt+F4, logging out) asks first when something would be lost or left unfinished: a connection with a transaction (`open`, `failed` or `unknown`), a query or an Apply still running in one of its tabs, query text or staged edits. Otherwise, and always after `app.quit`, the window closes at once. When it asks, the window stays and closes each open connection in turn (a window holds one today), with `connection.close {connection}` and its questions:

- A transaction: the transaction prompt (`transactionEnd`), about the connection, as above. A run in the transaction reads `Query 1 is still running in the transaction on Shop. Quitting stops it, so the transaction can only be rolled back.`, and after the prompt's first sentence comes what else quitting stops (an Apply), then what is lost.
- Else running work, query text or staged edits: `Quit anyway?` (`confirm`), with `dialog-ok` QUIT ANYWAY (a danger button) and `dialog-cancel`. `dialog-text` says what still runs first (`Query 1 is still running. Quitting stops it.`, `2 queries are still running. Quitting stops them.`, `The Apply on orders is still running. Quitting stops it, and nothing is written.`), then what is lost, as `needsConfirm` words it after its question (`The text of 1 query tab will be lost.`). QUIT ANYWAY closes the connection with `force`, which stops what runs.

COMMIT, ROLLBACK or QUIT ANYWAY closes that connection, then the next one is asked. CANCEL, or an end that fails (its error toast), stops the quit: the window stays, and the connection is as the answer left it. Once every connection has closed, the window waits for the work the closes stopped to end, at most 3 s, so the servers get the cancel requests, then closes.

## Rules

- Programmatic calls never open dialogs. `engine.execute` with empty params runs with defaults or returns an error; a command that needs an answer (a password, a host key) returns a `needs…` error with the details in `data`, and is run again with the answer in its params.
- Params are hostile input: wrong types, missing keys and deep nesting are errors, never panics ([never crash](standards/never-crash.md)).
- A read-only connection refuses, before sending, the statements that could turn read-only off or write in spite of it (`readOnly`), and when a statement turned it off all the same, the run ends with `readOnly` once dbee has rolled back and turned it on again. On Postgres a statement that turns `standard_conforming_strings` off is refused on every connection (`other`). A run stopped while dbee read the mode before a statement ends `cancelled`. A Postgres Apply after a function changed `client_encoding` writes nothing and fails (`other`) once dbee set it back to UTF8; applying again writes. So does one during which a trigger changed it.
- Passwords are never echoed in replies or the journal: `connection.parseUrl` answers `passwordGiven` (whether the URL had one), not the password. The log names methods and command ids, and the host and port of the database or SSH server a connection reaches, never params, SQL or values. A log file is private to its user (mode 0600 in a 0700 folder) where the OS has modes, and the lines of crates other than dbee's own (which an SSH server can influence) are written on one line, cut, and limited in number.
- A stored secret goes only to the settings it was saved for, which the secret store keeps with it. `connection.open`, `connection.test` and `connection.listDatabases` with any others, even by the saved connection's `id` when the connections file has changed, get `needsPassword`, `needsSshPassword` or `needsPassphrase`. The database a config names does not count: the password goes to the same server and the same user.
